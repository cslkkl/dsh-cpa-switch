## 0. 全景

本插件是 DSH 里 CLIProxyAPI（下称 CPA）的**管理控制台**：托管 CPA 进程、管理四个渠道的账号、执行养号（签到 / 任务 / 保活）。CPA 自带一个网页控制台（配置里 `openControlPanel` 控制是否自动打开），本插件把它的日常管理收进 DSH 面板。

### 0.1 从上游到本插件：七层

从上游到本插件是**单向依赖**的七层。下层不知道上层存在；改动只从上层往下传。

| 层       | 是什么                             | 例                                                       |
| -------- | ---------------------------------- | -------------------------------------------------------- |
| 上游     | 训练模型的公司（云端 API）         | 智谱、Kimi、MiniMax、DeepSeek                            |
| 渠道     | 转卖模型额度的平台                 | WorkBuddy / Trae / Qoder / ZCode                         |
| 渠道插件 | CPA 里对接各渠道的 dll             | `workbuddy.dll` / `trae.dll` / `qoder.dll` / `zcode.dll` |
| CPA      | 把各渠道聚合成一个 OpenAI 兼容服务 | 本地跑在 `:8317`                                         |
| DSH      | 你用的宿主平台                     | DeepSeek Harness                                         |
| pi-ai    | DSH 里管「模型 provider」的模块    | —                                                        |
| 本插件   | 连接 DSH 与 CPA 的桥 + 管理面板    | `dsh-cpa-switch`                                         |

### 0.2 本插件参与的两条流

**调用流**（你聊天时走的）：你选模型 → DSH(pi-ai) → CPA → 渠道插件 → 渠道 → 上游。

> 本插件**不在这条链上** —— 它只是提前把模型清单推给 DSH，让 DSH 知道有哪些模型可选。

**清单 + 管理流**（本插件做的事）：

```text
渠道插件 → CPA registry → /v1/models
                              ↑ 读
                          本插件
                              ↓ 推
                        DSH(pi-ai) → 选择器显示

本插件面板 ──→ CPA 管理 API（/v0/management/*）→ 改账号 / 签到 / 路由
```

> 本插件在这条链上是**中间人**：读 CPA、推 DSH；同时用 CPA 的管理 API 做面板。

### 0.3 本插件的三个角色

| 角色     | 干什么                                                    | 用到哪层       |
| -------- | --------------------------------------------------------- | -------------- |
| 桥       | 读 CPA 的模型清单 → 推给 DSH pi-ai（注册 `cpa` provider） | CPA → pi-ai    |
| 面板     | 显示 / 操作账号、签到、路由                               | CPA 的管理 API |
| 路由优化 | 给 CPA 生成别名表（防跨渠道轮询）                         | CPA 的配置     |

### 0.4 名字与层

同一个东西在不同层有不同的名字 —— 这是初看「很乱」的来源。按层看就清楚：

| 名字                   | 属于哪层                          |
| ---------------------- | --------------------------------- |
| `glm-5.3`              | 上游模型名                        |
| `WorkBuddy`（展示名）  | 渠道                              |
| `workbuddy.dll`        | 渠道插件（CPA 装载的）            |
| `wb/glm-5.3`           | CPA 生成的模型 ID 别名            |
| `cpa`（provider 键）   | 本插件在 DSH 里注册的 provider 名 |
| `CPA Switch`（展示名） | 上一条的 UI 展示名                |

上表 `cpa` 那行为什么只能声明键与展示名、profile 内容必须运行时算，见
[决策记录](../.agents/notes/2026-10-06-provider-key-runtime-not-patch.md)。

## 1. 两半结构

插件由**两半**组成，运行在完全不同的地方。这不是风格选择，是安全边界。

| 半边       | 入口                   | 运行位置           | 构建形态                   |
| ---------- | ---------------------- | ------------------ | -------------------------- |
| 宿主半端   | `src/index.ts`         | DSH 主进程（Node） | ESM → `lib/index.js`       |
| 浏览器半端 | `src/client/index.tsx` | 浏览器             | CJS 工厂 → `lib/client.js` |

浏览器半边**永远拿不到管理密钥**。它只调本插件的 `/api/v1/cpa/*`，由宿主半边带上密钥去调 CPA。

`lib/` 是**构建产物**，由 `pnpm build` 生成；`package.json` 的 `exports` 指向它。

## 2. 数据流：一次面板读取经过谁

```text
浏览器半端                    宿主半端                        外部
─────────                    ─────────                       ────
Panel / PluginPanel
  │
  ├─ useResource ──→ read-cache.ts 的读缓存
  │                  （fresh 30s / stale 300s）
  │                             │ 未命中
  │                             ▼
  └────────────────────→ GET /api/v1/cpa/*  ──→ Routes（route-table）
                                                  │
                                                  ▼
                                            ops/ 的五个域
                                                  │
                                                  ▼
                                          CpaGateway（通道）
                                        ┌─────────┴─────────┐
                                        ▼                   ▼
                                  CpaCache（5s）      CpaRuntime（探活记忆 1.5s）
                                        │ 未命中             │
                                        └─────────┬─────────┘
                                                  ▼
                                            cpaFetch（带管理密钥）
                                                  │
                                                  ▼
                                          CPA :8317 ──→ 上游渠道 API
```

三处**缓存**叠加在一条链上，各有各的生命周期 —— 这是「数字看起来没变」类问题的第一嫌疑点（见 §4.7）。页面刷新只清浏览器那一层；宿主那层要写操作才失效；**上游 CPA 自己也缓存**（`credits` 实测冻结 ≥3 分钟）。

反方向（写操作）的要点：写成功后宿主侧 `invalidateChannel()` 失效自己的缓存，浏览器侧 `invalidateReads()` 失效自己的，然后**重新回读**把权威值给界面 —— 不取请求值（§4.11）。

## 3. 两半与模块

**宿主半端**（Node）与**浏览器半端**（React）跑在不同进程，只通过 `/api/v1/cpa/*` 通信 —— 所以浏览器侧**永远拿不到管理密钥**，也不得 `import` 宿主的任何模块。

- **宿主半端模块逐个的职责 / 导出 / 被谁依赖** → [src/README.md](../src/README.md)
- **浏览器半端同上** → [src/client/README.md](../src/client/README.md)
- **环境准备（下载 / 校验 / 解压 / 写配置）** → [src/setup/README.md](../src/setup/README.md)

> 本节**不复制**模块清单 —— 清单在各自手册里，且随代码增删而变。
> 这里只说两件架构级的事：**为什么分两半**、**为什么某几个模块要独立成文件**。

### 3.1 为什么模块要这样切

**判「该合还是该拆」的三条尺子**（2026-10-05 边界重构定案），按顺序问：

1. **一起改的放一起** —— 改一个渠道要同时改四处，那四处就是**同一件事**（→ 合并）。
2. **不一起用的别绑一起** —— 只读面板用不到下载模块，绑进一个桶文件就是负债（→ 拆开）。
3. **漂了报不报错** —— 漂了**不报错**的必须机器钉死；会报错的允许重复（前者优先）。

一句话结论：**统一的是「事实」与「过程」，独立的是「变体」与「判据」**（下一段的实例）。

- **业务层按域拆成 `ops/` 五个文件，不再是一个大类**：原先 `Operations` 用类的理由是「这些操作共享两个前置，集中在一处就不会有某条路由忘了检查密钥」。前置搬进 `gateway.ts` 之后，类只剩下把互不相干的域粘在一起 —— 而拆开之后，`actions`（攒额度，作用于**全部**号）与 `enable`（只动调度面）的差别才看得见（F35）。域之间不许互相 import，共享的东西下沉到 `ops/result.ts`。
- **`gateway.ts` 是对 CPA 的唯一通道**：连接参数现取、就绪前置、读写、读缓存、失效五件事原先散在每个调用点，而**每处都能单独漂且漂了不报错**（漏一次现取 = 「改了端口要重启插件」；失效前缀与缓存键分开写 = 漏一个冒号就永远显示旧值）。收成一层之后调用点只写 `gateway.fetch(path, init)`，缓存键由 `cacheKeys` 产出、**键本身就是失效前缀**。见[决策记录](../.agents/notes/2026-10-05-cpa-gateway.md)。
- **`runtime.ts` 把「看」与「要」分成两个名字**：`status()` 只读探活、**绝不起进程**；`ensure()` 才可能按配置拉起。两者共用同一份探活记忆 —— 谁绕开它自己 `probePort`，面板的 `/status` 与那次判断就可能给出**相反**的答案。
- **纯判据独立于业务层**（`select-plan` / `checkin-ledger` / `action-outcome` …）：它们只做「输入 → 判据」，因此可以在 Node 侧直接测，也不需要网络与状态。越界由 `pnpm check:layering` 的 `judgement-no-io` 拦。
- **`channels/` 单独一层**：四渠道的余额单位、能力集、端点形态各不相同。渠道知识只登记一处（每个渠道一个 spec + 注册表），面板、路由、模型别名与生成配置全部派生，新增渠道不改路由层与 UI 层。
- **`state.ts` 纯文件读写**：无副作用、无网络，最容易测。
- **`setup/` 拆三段**：路径、配置生成、下载校验是三种不同的失败模式。
- **统一的是事实与过程，独立的是变体与判据**：渠道知识、配置字段、跨半契约、入口 id 属于「同一事实」，只能有一处登记、其余派生；就绪前置与缓存失效属于「同一过程」，只能有一条通道。判据是**漂了报不报错** —— 这几类漂了都不报错，所以必须用类型或测试钉死。
- **变体与判据各自独立**：四个渠道的接口形态、每类文案的翻译规则、每个交互的状态机互不相干，各占一个文件、共用同一个接口；新增一个变体只改一个文件，改一个渠道不碰别的渠道。
- **依赖方向单向且可校验**：契约 → 判据 → 能力 → 渠道 → 用例 → 传输 → 装配；浏览器半边只许依赖契约（`../contracts/`）。越界在构建期与测试期**都不报错**，所以由 `scripts/check-layering.cjs` 在 `pnpm check` 与 CI 上拦。
- **新增目录与「有独立规则可写」对齐，不与概念数量对齐**：每个可维护目录都要 `AGENTS.md` + `README.md` 双件，所以边界重构只新增 `contracts/` / `channels/` / `ops/` 三个；`client/` 子目录、`host/`、`http/`、`domain/` **一律不建**，先用命名前缀与守卫矩阵表达（2026-10-05 定案）。概念变多不等于该多开目录。

## 4. 契约边界（改动必须保形）

### 4.1 密钥边界

- 管理密钥只在宿主半边内存与 DSH 凭据库中。
- 浏览器侧路由**一律不带密钥参数**。
- 破坏此边界 = 安全缺陷，不是风格问题。

### 4.2 两条前缀不得混用

- 插件自身路由：`/api/v1/cpa/*`
- CPA 管理接口：`/v0/management/*`
- CPA 的 OAuth 接口：**`/v8/`**（不是 `/v0/`）

### 4.3 宿主路由契约（曾因违反它让插件完全不可用）

- 同一 `path` **只能注册一次**，多方法要在一条里合并；
- `ConnectionFetchMethod` 只有 `GET` / `HEAD` / `POST` 三档 —— 注册 `DELETE` 会抛异常。

违反任意一条，`register` 抛异常并**让所有路由都注册不上**（连 `/status` 都 404）。`src/routes.ts` 先归一化、再逐条 try/catch，就是为了兜住这个。

### 4.4 配置全字段 volatile

`Config` 的每个字段都是 `.volatile()`，两条理由缺一不可：

1. 只有 volatile 字段进得了设置表单；漏一个，那个字段就在卡片里消失（不报错）；
2. 写入路径按 volatile 逐路径放行，非 volatile 路径会被宿主直接拒掉。

副作用是好的：全字段 volatile ⇒ Loader 判「只有 volatile 变了」⇒ 改配置永不重挂，`apply` 只跑一次，值一律**现读**（不许缓存进字段）。

### 4.5 浏览器半端的导出面

`lib/client.js` 由宿主 `__ModuleLoader__.load({ factory })` 包装，必须导出：

- `apply(ctx)` —— 插件主体；
- `inject = ['slots', 'locale']` —— 服务门禁。**少它插件挂不上，且不报错**。

`react` 与 primitives 由宿主注入，**不能打进产物**（见 `tsdown.config.ts` 的 externals）。

### 4.6 模型路由只走 volatile 更新通道

- 模型路由由插件运行时推给 `llm-pi-ai` 的 `providers.cpa`（volatile 配置字段）：对它所在 loader entry 做**只含 volatile 差异**的 `entry.update()`，loader 在原进程内提交并广播 `loader/volatile-update`，llm-pi-ai 原子重注册路由 —— 不重启、不写盘。随包静态清单已废弃（会漂移、且与端口耦合）。
- **只动 `cpa` 一个键**：推送前合并既有 `providers`，用户自声明的其它 provider 原样保留；混入非 volatile 变更会让 update 退化成整体重载。
- **推送前等目录稳定**：CPA 启动后凭据分批加载，`/v1/models` 从空慢慢变多 —— 连续两次计数一致才推；目录为空（无账号）则撤下路由（`llm-pi-ai` 拒绝空 models 的手工路由）。
- 触发点：**插件装配完成**（零读推磁盘缓存里那份完整清单 —— 开机那一刻就有模型可选）、CPA 就绪（boot / 环境准备完成）、OAuth 加号完成，以及**宿主配置重载** —— 任何设置写入（切语言、改主题等）都会让宿主重建 fiber、抹掉运行时注入的 volatile 值，所以重载后必须重推（机制见 F39）；幂等，无变化即零动作。
- **写盘与推送之前过一道「目录护栏」**（F49）：清单只许**长**、不许莫名变短。缩水有两种 —— 读残了（拦下、有限重读）与合法地少了（跳过 / 不可用的渠道，放行）。

### 4.7 读路径有两级缓存，且失效是**事件**

面板每点一次会打 6 条路由（`status` / `plugins` / `setup` / `accounts` / `auto-checkin` / `routing`），而每条在宿主侧都要先 `ensure()` 探一次活。**没有缓存时，用户看到的「点一下等很久」就是这个乘法。**

| 级         | 位置                                                       | 作用                                                    |
| ---------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| 探活记忆   | `cache.ts` `ProbeCache`                                    | 折叠**同一次点击**里 6 条路由的探活，只开 1 个 TCP 连接 |
| 业务读缓存 | `cache.ts` `CpaCache` / 浏览器 `read-cache.ts` `ReadCache` | 复用刚读到的账号、余额、策略                            |

三条必须保住的性质，**都不抛错、只会静默变慢或显示旧值**：

1. **同一 key 的并发合并成一次**（single-flight）。少了它，挂载时同时到的 `/accounts` 与 `/auto-checkin` 会各打一次 CPA。
2. **每个改变 CPA 状态的写操作成功后要失效**。`gateway.invalidateChannel()` 是宿主侧的出口；浏览器侧由 `endpoints.ts` 的**写函数自己**调 `invalidateReads()`（`accounts:` / `autockin:` 两个前缀，必须与宿主 `cacheKeys` 造出的键一致）。漏一处 = 用户点完签到看到的还是旧余额。
3. **失败不写缓存**。否则一次抖动会把错误缓存住整个 TTL。

失效用**前缀**而不是精确 key：`account-select` 会改**同渠道全部**账号的启用状态，精确失效会漏掉它们。空串前缀表示「不知道影响哪个渠道」，按全部失效处理。

⚠️ **一个渠道有几个 key，清漏一个就是「看起来没生效」**。键的形状与失效清单**必须同源** —— 两者都由 `gateway.ts` 的 `cacheKeys` 产出，键本身就带分隔冒号，于是「键」直接当「前缀」用，既不会漏掉自己的读、也不会误伤 id 是它前缀的渠道。手工在取数处与失效处各写一遍字符串，就是那条 `autockin:` 漏冒号的老路（实踩）。

> **切渠道不闪**与**页面预取四渠道**的具体做法（渲染阶段同步 `peek` 缓存、`Panel` 刻意不加 `key`、已取到的值连 key 一起存、`freshMs = 30s` 的取舍、预取触发点）写在 [src/client/README.md](../src/client/README.md) 与[决策记录](../.agents/notes/2026-10-04-channel-switch-read-strategy.md) —— 那是浏览器半端的实现约束。此处只留架构级的两条：**失效靠事件、不靠时间**；**两级缓存叠加在一条链上**（见 §2）。

### 4.8 浏览器半边必须有渲染错误边界

宿主的槽位渲染带自己的 error boundary，而那个 boundary 是**锁存的** —— 子树抛过一次之后，那块区域在这次挂载的整个生命周期里都没了，用户的唯一退路是禁用再启用插件。所以本插件在每个槽位外面包一层 `PanelBoundary`。

它必须是**类组件**：React 规定 error boundary 用 `getDerivedStateFromError` / `componentDidCatch`，两者都没有 hook 等价物。这是 `PanelBoundary.tsx` 唯一的存在理由，也是 `scripts/verify-artifacts.cjs` 的 shim 里必须提供 `react.Component` 的原因（缺了它，产物在工厂执行时就会抛）。

### 4.9 上游数据不能改，只能适配

**上游是 CPA**：一个独立进程。插件启动它、调用它的管理接口，但**插件不含它的任何代码**。所以上游返回什么，插件**改不了**——只有两个选择：**翻译**，或**原样透传**。

三条规则：

1. **只实测过的值才映射。** 映射表是「已核对过的取值集合」，不是猜测。
2. **认不出的原样透传。** 上游随时会新增档位、改枚举文案；透传最多是不好看，猜着翻则是**显示错误信息**——比不好看糟得多。
3. **不翻译用户自己的数据。** 昵称、套餐包名这类是用户的数据，替他翻译等于篡改他看到的东西。

**为什么**：上游不受本仓控制、随时会变。一张凭想象补全的映射表看起来更"完整"，实际上是把未知当成了已知 —— 出错时它不会暴露，只是**安静地显示错的字**。

实例（`plan` 字段，见 [决策记录](../.agents/notes/2026-10-04-upstream-value-translation.md)）：`免费 → Free`（实测）、`coding-plan` 原样（实测），`basic` / `pro` / `premium` 暂在表内但**尚未实测**——留着无害（匹配不到），删掉也无害，只是别把它们当已确认的事实。

### 4.10 样式只能来自宿主 token

`panel.module.css` 里的每个值要么是 `--dsw-*` token，要么是从宿主 `settings-form/fields.module.css` 抄来的数字。**不写颜色字面量**，明暗两套主题因此自动跟随。

⚠️ **`--dsw-alias-bg-layer-N` 只定义到 3**。宿主自己的 `fields.module.css` 引用了 `--dsw-alias-bg-layer-4`，那个键**不存在** —— 别照抄那个引用。

按钮、开关、标签、状态点、页签、弹窗、Toast 一律用 primitives，不自绘：自绘要重做焦点环、禁用态与明暗切换三件事。

**分工：CSS 声明「是什么样」，TS 决定「值是多少」。** 样式的本质是声明，不是逻辑 —— 编译期就确定的秩序交还 CSS，只有运行期才知道的数值交给 TS，两者在边界上只以「值」握手。于是：动画参数（光带宽度、周期、缓动、颜色）与骨头的宽高全在样式表；TS 只给「这是哪个槽位」「几张骨架卡」这类值（见 [src/client/README.md](../src/client/README.md) 的骨架一节）。

⚠️ **自定义属性不会被 CSS Modules 改名**（只有类名与 `@keyframes` 会），而注入的样式表是全局的 —— 本仓的自定义属性一律带 `--cpa-` 前缀，且不写在 `:root` 上。不带前缀就会与宿主的同名属性撞车，而撞车**不报错**、只是值变成宿主的。

**首屏骨架（`.skeletonBlock`）的两条硬约束**（[决策记录](../.agents/notes/2026-10-07-panel-skeleton-shimmer.md)）：

- **扫光挂在「块」上，不在骨头上** —— 挂骨头上时「光带宽度 ÷ 骨头宽度」会决定动效的**种类**：窄骨头只能整块亮起再暗下，宽骨头却是滑动，同一张卡里同时播两种动效，且行程随骨头宽度变（`translateX(100%)` 是相对元素自身宽度）。
- **动画层必须与块同宽**（`inset: 0`）。层若设成光带宽度，`100%` 只走光带那么远，光带在宽块上永远出不去右侧，循环衔接处就跳。

### 4.11 值的来源：写成功后的界面值只认后端回读

**不取请求值**（「我们以为写进去了什么」）、**不取本地意图文件**（CPA 侧被别的东西改过就过期）。只有**回读值权威**（F33）。

两条落地：

- **写操作要能容忍部分失败**：`PATCH /auth-files/status` **一次只改一个文件、上游没有批量接口**，写没有事务 → 逐个写要**各自容错** + **回读确认**；「设为唯一」的 `ok` 判据取**目标号最终是否启用**（那才是它的意图），个别其余号没禁成属降级不致命（F43）。
- **即时覆盖层必须「后端一确认就自我删除」**：它的使命是「写完到重读之间不撒谎」，不是长期真相；留着就会永久压住后端值。两条路径的键不同 —— 单卡开关用 `authIndex`，「设为唯一」用**凭据文件名**（`authId`），查表时**两个都要查**。

> 卡片**外观**的具体规范（六槽位与定高算式、状态标签色、禁用降级、控件样式、文案标点与 Emoji）是**模块级**约束，写在 [src/client/README.md](../src/client/README.md)；判据 `tests/card-slots.test.ts`。本节只留「值从哪来」这条跨模块原则。

类名是**哈希**的（`[hash]_[local]`）。注入的样式表是全局的，而宿主页面自己也有类名 —— 哈希之后一次改名就不可能与宿主某条规则撞上，而撞上会静默地把卡片改成另一个样子。

⚠️ **别断言哈希的具体形状**（`/[A-Za-z0-9]{5,}_card/` 这种）。`[hash]` 由 lightningcss 从样式表的**绝对路径**算出，同一份源码在不同 checkout 下哈希不同；而且哈希以数字开头时 CSS 标识符会被转义成前导下划线（`1gY9Cq` → `_1gY9Cq`）。本机恰好算出字母打头的 6 位值、CI 算出别的 —— 于是判据**本机绿、CI 红**（实测踩过）。稳定的只有 `[local]` 那一半（`card` / `grid` / `wrap` …），断言要锚在它上面。

## 6. 文档网络

### 6.1 分层约定

- 根 `README.md`：门面，面向使用者。
- 根 `AGENTS.md`：维护索引，面向 agent。
- 本文件：设计圣经，写「为什么」。

- `调研报告归档/`：**已 gitignore 的只读历史**，不属文档网络、不建双件。

### 6.2 引用约定

- 一律相对路径，禁写本机绝对路径。
- 跨文档引用默认指向整个文档，不写「第 n 节」。
- 文档网络改动后跑链接校验，命令见根 [AGENTS.md](../AGENTS.md)。

  ⚠️ 原 P7 里的另外两件**改行为**，不属纯物理迁移，已各自立项，并都在 2026-10-06 按「先补判据再动结构」收口：**状态文件写入单入口**（判据先证明旧写法会吞记录；读改写是一个同步块，不再有「快照跨越 `await`」，见[决策记录](../.agents/notes/2026-10-06-state-single-entry.md)）；**模型路由的等待**（退避 / loader 轮询 / 耗时计时都走注入的 `Clock`，默认真实计时器、生产行为不变，「等到上限就收场」随之可断言，见[决策记录](../.agents/notes/2026-10-06-route-clock-injection.md)）。见[下一步计划](PLAN.md) §2.9。
