# 决策：模型清单在**装配那一刻**就推（2026-10-07）

状态：生效

## 问题

维护者反馈：**每次开机启动 dsh**，第一条消息必报
`pi-ai provider "cpa" has no configured model "wb/deepseek-v4.1-flash"`（`UNKNOWN_MODEL`），
**重新打开 dsh web 才好**。截图里三条红点，其实是两件事。

### 实机时间线（2026-10-07，会话记录 + CPA `startup.log`）

| 时刻     | 发生了什么                                                              |
| -------- | ----------------------------------------------------------------------- |
| 19:04:45 | 会话建立（这一次启动之后）                                              |
| 19:04:58 | 第一条消息 → `UNKNOWN_MODEL "wb/deepseek-v4.1-flash"`（建会话后 13 秒） |
| 19:05:06 | 用户手动把模型切成**裸名** `deepseek-v4.1-flash`                        |
| 19:05:29 | 再发 → CPA 返回 `400 unknown provider for model deepseek-v4.1-flash`    |
| 19:05:42 | 重开 dsh web（新进程；插件 19:05:44 重新拉起 CPA）                      |
| 19:05:45 | 插件开始读目录（13 条凭据逐个读 + `/v1/models`）                        |
| 19:05:51 | 再发 → 仍 `UNKNOWN_MODEL`（这次是裸名）                                 |
| 19:06:00 | 用户切回 `wb/deepseek-v4.1-flash` —— **选择器到这时才有内容**           |
| 19:06:03 | 完整清单才真正推上去（同秒 CPA 侧别名段被改写）                         |

### 两个成因，一个窗口

1. **`providers.cpa` 的静态骨架没有 `models`**（[cordis.patch.yml](../../cordis.patch.yml)
   刻意不写：清单随账号增减、且与端口耦合）。清单只能由插件运行时推 ——
   而选择器读的就是 `providers.cpa.models`，所以这段窗口里**一个模型都没有**。
2. **推清单挂在「CPA 此刻在不在跑」上**。`boot` 的顺序是「(补装环境) → `ensure()` 等
   CPA 起来 → 恢复账号意图 → 开机补签 → 推清单」，旧写法只在 `state.running` 为真时推；
   `ensure()` 的预算（`startTimeoutSeconds`，默认 30s）用尽时**只 warn 一句、
   永不推清单**，也没有重试。于是磁盘上那份完整清单白躺着，用户只能靠
   「重开 dsh web」或写一次设置去撞 `config-reload`。

第三条红点（裸名 `deepseek-v4.1-flash`）是**另一件事**：同名模型被多渠道供给时
路由 id 是**渠道别名**（`wb/…`），裸名不再是合法 id。它不会自愈，对策是重选一次模型
—— 不属本篇。

## 决策

**「上次完整成功过的那份清单」要在插件挂上来的那一刻就推出去，不等任何人。**

1. **装配即推**（`attachRouteRegistry`）：读到磁盘缓存后立刻 `pushProfile(…, 'boot:cache')`
   —— **零 CPA 读**（一次 volatile update 往返），失败只记日志（`llm-pi-ai` 条目还没挂上
   是装配期的正常情形，随后 `boot` 那次会补）。
2. **`boot` 推清单不再看 `state.running`**：`refresh` 内部本来就处理「CPA 没跑」
   （回退上一份成功清单、没有历史才保持空），所以无条件调它才是对的语义；
   顺带**把结果记进日志**（从前返回值被丢掉，「清单没推上去」零痕迹）。
3. **序号护栏判在「等到条目之后」**：装配即推会与后来的推送并发，前者若卡在
   `findEntry` 上，醒来时手里那份已经旧了 —— 判在等待之前会用旧清单盖回新的、
   还把 `pushedSeq` 一起倒退。

## 替代方案（强制）

- **只把 `boot` 那次改成无条件推**：装配到 `boot` 之间仍有「等 CPA + 恢复账号 + 补签」
  的窗口，第一条消息照样可能落在窗口里。**否决为唯一手段**（保留它作为补救与新鲜读）。
- **在 `boot` 里加一个「提前推」步骤、走 `refresh`**：会顺带读 CPA（装配期多半白读），
  且把同一件事拆成两个机制。**否决** —— 用同一个原语 `pushProfile`，不新开路径。
- **给 `ensure()` 加轮询 / 定时重试**：与「恢复逻辑挂事件、不挂时机」的既有口径冲突
  （PLAN §2.6.0 那个定性问题，当时就是这么绕开的）。**否决**。
- **装配时「等一会儿再推」**：同样是把窗口用等待填上，口径问题照旧。**否决**。
- **把 `models` 写回静态骨架**：清单会漂（账号增减、别名随渠道变化）且与端口耦合，
  早已否决（[启动不等读那篇](2026-10-06-startup-does-not-wait.md)）。**否决**。
- **修 `ensure()` 的预算（调大 `startTimeoutSeconds`）**：只是把窗口挪长，CPA 真起不来时
  照旧空着。**否决**。

## 影响

- **收益**：有缓存时，DSH 一能用就有模型可选 —— 开机第一条消息不再撞空骨架；
  「没能推上清单」在日志里留痕（`cpa-panel: model routes at boot …`）。
- **代价**：装配期多一次 volatile update（零读，价同 `config-reload` 的快路径）；
  `llm-pi-ai` 条目若还没挂上会多一条 warn，属正常且随后会被 `boot` 那次补上。
- **边界**：**没有缓存**时（首次安装、缓存损坏、端口改过、版本不符）仍然只能靠读；
  那一档由目录护栏 + 有限重读覆盖（[目录护栏那篇](2026-10-07-catalog-shrink-guard.md)）。
- **判据**：`tests/boot.test.ts`（6 条：CPA 没起来时也必须推、账号意图与补签仍只在
  CPA 在跑时做、就绪时顺序不变、推送失败要留痕、成功不许当异常喊、卸载后不再动手）+
  `tests/route-registry.test.ts` 的「装配即推缓存清单」「没有缓存时装配不推任何东西」
  「装配即推迟到时不覆盖后来推上去的新清单」。
- **真机验收**：需重启 DSH（宿主半端不随页面刷新加载）。验收点：开机后在**发第一条消息
  之前**，终端已出现 `model routes boot:cache` 与 `模型路由 … models`，且选择器有模型。
