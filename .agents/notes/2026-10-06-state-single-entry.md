# 决策：状态写入收成单入口读改写（2026-10-06）

状态：生效

## 问题

立项要求「先补判据再动结构」，判据先写，两条**当场就红了** —— 两个 bug 都是真的：

**一、丢更新：开机补签吞掉窗口里发生的签到。**
`cpa-panel-checkin.json` 一个文件装两件事（渠道级补签日期 + 账号级今日账本），
补签的顺序是「读账本 → 等 CPA 回话 → 写账本」，而**读之后、写之前有 `await`**。
用户在这个窗口点一下签到，补签醒来就用**旧快照整份覆盖** —— 用户那次记录没了，
界面接着显示「未签到」（正是这份账本存在的理由），而**磁盘上一切正常**。

**二、写入口让「读的内部信号」落盘。**
`readAccountIntent` 会带出 `ignored`（「这份文件不可信」），注释写着它「绝不写回磁盘」；
但写入口是整份覆盖，调用方把读出来的对象原样交回去（`rememberIntent` 就是这么写的），
`ignored: 'untrusted-source'` 就进了文件。今天不致命（可信文件读时还会再剥一次），
但它让「磁盘上没有这个字段」只靠调用方自觉 —— 而不变量一旦靠自觉就等于没有。

## 决策

写入**只有一种形状**：`updateXxx(改法)` —— 读当下的内容 → 交给调用方改 → 立刻写回，
**整段同步、中间没有 `await`**。

- 传的是**函数**而不是算好的值。这是不变量的全部机制：值只能来自更早的某次读，
  而更早的读就是那个坑。
- 删掉三个整份覆盖的写函数（`writeStamp` / `writeCheckinLedger` / `writeAccountIntent`），
  调用点只有三处，全部改成传改法。
- `readStamp()` 返回类型化的 `CheckinStamp`：解析只有一处答案，**认不出的字段原样带走**。
- `updateAccountIntent` 在**写入口**剥 `ignored` 并把 `source` 固定为 `panel` ——
  两头都剥，才不用指望调用方。
- `startupCheckin` 收尾**只写一次**，两个字段一起改（拆两次写会重新打开同一个窗口）。
- 判据先到位：`tests/state-lost-update.test.ts` 两条先写成 `it.fails` 证明 bug 存在
  （交错用 deferred 卡住请求做到**确定性**，不赌机器快慢），改完摘掉 `.fails` 当防回归。

## 替代方案（强制）

- **加读写锁 / 写队列**：进程内不需要 —— 读改写收进一个同步块后，Node 单线程根本不会交错；
  队列只在「读和写之间必须 `await`」时才有用，而那种形状正是这次要消灭的。
- **跨进程加锁（lockfile）**：这些文件只由本插件写、DSH 单实例；加锁要处理陈旧锁、
  崩溃残留、Windows 上删不掉的锁文件 —— 复杂度换一个不存在的场景。
- **保留整份覆盖的写函数，靠 review 把关**：这正是本次两个 bug 的成因，
  尤其第一个是「顺手把读提前到 `await` 之前」写出来的，**失败无声**。
- **只修 `startupCheckin`（最小补丁）**：留着一族同形状的写入口，`rememberIntent`
  已经踩着第二个坑了 —— 修一个坑、留一族坑不是收敛。
- **顺带做原子写（临时文件 + rename）**：本次判据里的「序列化失败不留半个文件」已由
  「先序列化再写」满足；崩溃/断电级别的半个文件是另一个问题（还要处理 Windows 的
  rename 覆盖语义），不混进这批。

## 影响

- 判据：[`tests/state-lost-update.test.ts`](../../tests/state-lost-update.test.ts) —— 6 例，
  覆盖「补签不吞窗口里的签到」「写入口不落 `ignored`」「两个号重叠签到都要在」
  「开工前就有的记录不被吞」「序列化失败不留半个文件」。
- **留下的纪律**：新增状态字段时用 `updateXxx(改法)`，**不要**加「整份覆盖」的写函数；
  真需要跨 `await` 时，`await` 之后再用改法重取一次，别把读提前。
- 对外行为不变（消失的只有 bug）；接口收窄：三个 `writeXxx` 换成三个 `updateXxx`，
  调用点三处（`src/ops/actions.ts` 两处、`src/ops/enable.ts` 一处）。
- 边界：进程内不交错；跨进程无锁（同上）。
