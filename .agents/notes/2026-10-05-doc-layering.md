# 决策：文档分层收窄 —— 架构文档只管宏观，模块细节下沉（2026-10-05）

状态：生效

## 问题

维护者指出两件事，实测后确认都成立：

1. **根 [AGENTS.md](../../AGENTS.md) 的活跃坑塞了大量不属于它的东西** —— 34 条占 160 行，但其中
   约 20 条是**卡片/文案设计规范**、2 条是**运维杂项**，只有约 10 条是真正的
   「不知道就会踩、踩了没信号」的陷阱。
2. **`docs/ARCHITECTURE.md` 直接跳到模块细节** —— 413 行里有整节「模块划分」
   （42 行，逐模块列职责）与三节卡片外观规范（约 90 行），而**没有宏观数据流**。

两者的共同后果：**该在一个粒度上找的东西，散在另一个粒度上**。
[AGENTS.md](../../AGENTS.md) 每次会话都注入，噪音会淹掉真陷阱；架构文档本应是「先看大图」的地方，
却先让人读模块清单。

## 决策

按**读者在什么粒度上找它**重新划 home，并写进
[架构说明](../../docs/ARCHITECTURE.md) §6.3（信息 home 划分）：

| 事实                                                              | home                                                 |
| ----------------------------------------------------------------- | ---------------------------------------------------- |
| 宏观数据流、大架构、**跨模块**契约与不变决策                      | [架构说明](../../docs/ARCHITECTURE.md)               |
| 逐模块职责 / 导出 / 改哪 / **模块级规范**（样式、卡片、状态表达） | 对应子目录的 [README.md](../../src/client/README.md) |
| 「不知道就会踩、踩了没信号」的陷阱                                | 根 [AGENTS.md](../../AGENTS.md) 活跃坑               |
| 成轮工作、未立项方向                                              | [PLAN.md](../../docs/PLAN.md)                        |
| 「当时为什么这么定」、替代方案                                    | [决策记录](.)（本目录）                              |

四处具体动作：

1. **架构文档新增 §2「数据流」** —— 一张文字流程，把浏览器 → 宿主 → 两级缓存 →
   CPA → 上游 这条链和「三处缓存各有生命周期」讲清楚。这是此前缺的宏观视角。
2. **架构文档删掉 §2「模块划分」两张表**（42 行）—— 内容在子目录 README 里本来就有，
   改成一行指针。清单随代码增删而变，抄一份就得多跟一份。
3. **架构文档的卡片外观规范（约 90 行）下沉到 `src/client/README.md`** ——
   架构文档只留「值从哪来」这条跨模块原则（§4.11 只认后端回读），
   外观细节（六槽位定高算式、状态标签色、禁用降级、控件样式）归模块手册。
   顺带发现 `src/client/README.md` 里那段「卡片等高靠 `grid-auto-rows` +
   `margin-top: auto`」是**已失效的旧机制**，一并改掉。
4. **活跃坑 160 行 → 59 行**，按四类重组：静默失败 / 环境与运行 /
   改动前先读的契约 / git 相关；有决策记录的条目压成一行 + 指针。

## 替代方案（强制）

- **只删不搬**：信息会丢。卡片规范是真约束（改错会让卡片参差），
  只是不该在架构文档那一层。
- **给架构文档再加一个「模块细节」章节**：只是把问题换个地方 —— 架构文档仍然不是
  宏观视角，读者仍要跳过模块清单才看到设计。
- **新建 `docs/cards.md` 之类的专题文档**：卡片规范属于 `client/` 这个模块，
  放模块手册里「改哪查哪」两跳可达；单开一个文档要多一处维护、少一条从模块出发的路径。
- **活跃坑保留全部、只重排序**：行数不变，会话注入的噪音不变，
  真陷阱仍会被淹没。

## 影响

**收益**：

- 架构文档从 413 → 353 行，且**读起来是自上而下的**：数据流 → 两半与模块 →
  契约 → 防错 → 已知局限。
- 活跃坑 160 → 59 行，每类有明确判据；[AGENTS.md](../../AGENTS.md) 每次会话少注入约 100 行。
- 同一事实只有一个 home，跨文档引用改为**指向文档**而不是「第 n 节」
  （节号会随重排失效 —— 这次重排就踩到了，[AGENTS.md](../../AGENTS.md) 原先指向 §4.10–4.13）。

**代价**：

- 卡片规范的路径变长一跳（先到 `src/client/README.md`）。可接受：
  改卡片的人本来就在 `src/client/` 下工作，[AGENTS.md](../../AGENTS.md) 与根索引都能两跳可达。
- 需要维护者对「这条该放哪一层」有共识 —— 判断标准已写进架构文档 §6.3，
  不靠记忆。

**验证**：文档网络链接校验 0 error / 0 warning（188 条链接）；
`pnpm check` 全绿（typecheck ×2 / lint / format / build / 产物断言 28 / test 234）。
