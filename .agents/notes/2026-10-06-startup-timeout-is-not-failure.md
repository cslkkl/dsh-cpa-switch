# 决策：启动超时不是启动失败（2026-10-06）

状态：生效

## 问题

DSH 与 CPA 的启动顺序**没有保证**，而启动流程曾把 `ensure()` 的返回当成终结。

实测时间线（2026-10-06，本机）：

```
13:49:11  DSH 启动 → boot.ts:84 runtime.ensure()
              ↓ spawn → waitForPort(port, 30_000)
13:49:41  30 秒到 → 返回 { running: false, owned: true, reason: 'start-timeout' }
              ↓ boot.ts:117 只 warn 一句 → runBoot 结束
13:50:05  CPA 才真正开始监听（比 DSH 晚 54 秒）
13:54     用户选模型 → providers.cpa 停在空骨架 → UNKNOWN_MODEL
```

`startTimeoutSeconds` 默认 30（`config.ts:33`），这次 CPA 用了 54 秒。

**根因不在「没有重试」，而在「超时被当成了失败」。** 超时那一刻**子进程还活着**
（`CpaProcess` 的 `#child` 仍在），它不是起不来，只是比我们的耐心慢。
而旧实现在 `finally` 里把 `#starting` 清掉，于是**下一个调用方以为没人起**，
重新走 spawn 分支 —— 它等的是同一个永远等不到的东西。

症状是**静默**的：面板显示 CPA 可用，模型清单却是空的。用户报的是
`pi-ai provider "cpa" has no configured model "wb/…"`（`UNKNOWN_MODEL`）。
之所以后来自己好了，是某次设置写入触发 `app-boot/config-reload`
（`route-registry.ts:650`）把清单补上了 —— **恢复靠的是巧合，不是设计**。

## 决策

把不变量从「超时后没人再管」改成 **「超时只是预算用尽，等待可续」**：

1. **超时不丢弃「正在起」的记忆** —— `ensure()` 探到端口不通时，
   先看有没有**本插件拉起且仍活着**的 child（`#owned && exitCode === null`）；
   有就**继续等它**，不再 spawn。
2. **死进程必须被丢弃** —— 同一个判据要求 `exitCode === null`；
   探到 child 已退出就地清掉记忆，下次调用自然重新 spawn。
   这条是反向保险：少了它，一次崩溃会让插件对着死进程**永远空等**，比原 bug 更糟。
3. **等待由用户动作驱动，不引入轮询** —— 面板每条请求都经
   `gateway.requireRunning()` → `runtime.ensure()`，所以「用户打开面板 / 点刷新」
   本身就是重试机会。**一行 `setInterval` 都没写**，符合
   「恢复逻辑挂在语义上、不挂在时机上」的既定口径。

实现上把注入点做成**可选**字段（`ProcessDeps` 的 `probe` / `spawn` / `resolveExe` /
`pollIntervalMs`），不传时生产行为逐字不变 —— 与 `Clock` 同一套做法
（[决策记录](2026-10-06-route-clock-injection.md)）。

## 替代方案（强制）

- **把 `startTimeoutSeconds` 默认值改大（如 120）**：最省事，但不解决语义 ——
  CPA 慢到 121 秒照样卡死，且每次冷启动**无条件多等**（用户根本不开面板也等）。
  否决。⚠️ 但本决策落地后单次预算**可以调小**：等待可续了，
  「一次等多久」不再是「总共等多久」。两者互补，不是替代。
- **订阅 CPA 的「启动完成」事件**：**CPA 没有这个事件**。唯一的健康端点
  `GET /healthz`（`internal/api/server_routes.go:44-53`）是写死的
  `{"status":"ok"}`、无推送面；要用它就得轮询 → 违反约束。否决。
  （附带事实：CPA 的启动顺序是**先加载凭据、最后才起 HTTP server**
  （`sdk/cliproxy/service_lifecycle.go:71→168`），所以 `/healthz` 能连通时
  凭据其实已就绪 —— 它比 `probePort` 是**更强**的就绪判据。本决策不顺手改它，
  避免把判据改动混进行为改动。）
- **`boot.ts` 超时后开后台定时器重试**：直接违反「不轮询」；且 CPA 若因配置错误
  永远起不来，定时器会一直转下去刷屏日志。否决。
- **`boot.ts` 超时后 `setTimeout` 一次性重试**：比轮询好，但仍是**猜一个时机**
  （60 秒凭什么？），且只在 boot 那一次 —— 用户 5 分钟后才开面板时，
  那次重试早已白跑。否决（属「挂时机」）。
- **解析子进程 stdout 抓 `API server started successfully`**
  （`service_lifecycle.go:177`）：**这是唯一真正的 CPA 就绪事件**，方向正确。
  但代价是 `stdio: 'ignore'` 要改 pipe（不接住输出会写满管道卡死子进程），
  且要解析随上游漂的文案；何况那行是 `time.Sleep(100ms)` **之后**才打印，
  与实际可服务之间仍有缝。**本期否决，留作未来方向。**
- **面板侧检测到空清单就自动重试**：把恢复逻辑放到前端 = 又一个「时机」，
  且多端（刷新页面 / 换浏览器）行为不一致。否决 —— 恢复必须在宿主半端。

## 影响

- **代价**：`CpaProcess` 多了一个「child 未就绪」的判据，并发 `ensure()` 的语义
  略复杂。这是本决策唯一的复杂度来源，由 8 条判据钉住。
- **收益**：CPA 慢启动不再需要用户「随便改个设置」来唤醒；等待由用户动作驱动，
  不引入任何后台轮询。
- **不解决**：CPA **起不来**（exe 缺、配置错）时的空清单 —— 那是另一回事，
  面板已有 `reason` 显示。
- **判据**：`tests/process.test.ts` 8 例（注入 seam 后 170ms 跑完；用真实
  400ms 轮询要 13s）。**变异验证**：把「继续等」那条分支短路掉，
  「超时不重复 spawn」「等待可续」「连续超时都报 start-timeout」三条转红，
  而「死进程可重新 spawn」**保持绿** —— 证明后者守的是另一条轴，不是同一条判据的重复。
- **真机验收**：需重启 DSH（宿主半端不随页面刷新加载）。
  ⚠️ **攒批验收**：与 Bug A（别名机制）以及其他需重启的改动**一次验完**。
