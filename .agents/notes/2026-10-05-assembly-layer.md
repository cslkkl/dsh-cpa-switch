# 决策：装配层只挂线（2026-10-05）

状态：生效

## 问题

`src/index.ts` 是 637 行，而它自称「只做装配」。实际内容四块：

| 块                                                                | 行数级 | 它其实是什么           |
| ----------------------------------------------------------------- | ------ | ---------------------- |
| 生命周期流程（备凭据 → 补环境 → 拉起 → 恢复账号 → 补签 → 推路由） | ~90    | 一个**宿主时机**       |
| 环境准备的运行态（`{running, progress}`）+ 一键准备流程           | ~60    | 一次安装的**运行态**   |
| 路由表（16 条、每条带业务说明的 handler）                         | ~300   | **传输层的声明式数据** |
| 真正的装配（造对象、挂 effect、注册路由）                         | ~40    | 装配                   |

混在一起的代价不是「文件长」，而是**改动的影响面看不出来**：
改一条路由的注释要翻到文件后半段，改启动顺序要翻到中间，而两者在同一份 diff 里没有边界。
它也违反仓库自己写在 [src/AGENTS.md](../../src/AGENTS.md) 的「`index.ts` 只做装配」。

## 决策

四块各回各家，`index.ts` 只剩装配（约 185 行）：

- **生命周期流程 → [`src/boot.ts`](../../src/boot.ts)**：`runBoot(deps)` 收依赖与 `isCancelled`。
  每一步的「被卸载就停」判断原样保留（12 处）。
- **环境准备运行态 → [`src/setup/session.ts`](../../src/setup/session.ts)**：
  `inspect()` / `run()` / `autoInstall()` 三条语义各有入口；
  原先两处重复的 try/catch 与「一键准备」那段流程收进同一个类。
- **路由表 → [`src/route-table.ts`](../../src/route-table.ts)**：声明式数据；
  handler 只做「解码 → 调用例 → `json()`」。
- **`setup/index.ts` 从「既是桶又是实现」改成纯转出**：主流程进 `setup/prepare.ts`。

## 替代方案

- **保持现状，只把注释整理好**：影响面问题不是注释能解决的 —— 一次启动顺序的改动
  与一次路由改动在同一份文件里，review 时无法按块看。
- **只搬路由表**（收益最大的一块），生命周期留在原处：`index.ts` 仍有 ~150 行流程，
  「只做装配」这句仍然是假的，而下次改动还会问「启动逻辑在哪」。
- **引入路由框架 / 装饰器**：为 16 条路由引一个抽象层，收益是少写几行 `methods`，
  代价是多一个概念与一层间接；本仓零依赖，不为这点重复引框架。
- **把路由表按资源拆成多个文件**（`routes/accounts.ts` 等）：16 条路由分四份，
  每份都要重复 import 同一组依赖，且「所有路由放在一张表里看得见冲突（path 唯一）」
  这个好处会消失 —— 那张表本身就是判据。

## 影响

- 新增路由 = 在 `route-table.ts` 的表里加一条 + 回填 [src/README.md](../../src/README.md) 的表
  （后者由 `tests/route-table.test.ts` 判据钉住，忘了回填会红）。
- 改启动顺序只看 `boot.ts`；改准备流程只看 `setup/session.ts`。
- `index.ts` 的 `apply` 现在三分钟能读完：造四个对象 → 挂两个 effect → 注册路由。
