# 决策：关闭档位的拼写按渠道给（zcode 用 `none`，不是 `off`）（2026-10-06）

状态：生效

## 问题

「思考档位」只暴露两个值：关（`off`）与开（`high`）。但 **`off` 不是所有渠道都认的词**。

实测（2026-10-06，`POST /v1/chat/completions`）：

```
model=zcode/glm-5.2  reasoning_effort=off
→ 400 upstream 400: {"error":{"code":"1210","message":
    "reasoning_effort must be one of: none, minimal, low, medium, high, xhigh, max"}}
```

`zcode` 的合法词汇表里**只有 `none`，没有 `off`**。而本插件硬编码的是
`REASONING_EFFORTS = { off: 'off', high: 'high' }` —— 于是**在 zcode 渠道上选「关」
必然 400、整轮对话失败**。

这正是 `AGENTS.md` 记着的那个坑（上游对推理档位返硬错误让整轮会话失败），
只是这次不是「上游抽风」，而是**我们的值本来就写错了**。

## 决策

**「关」这个档位发出去的值，按渠道给：workbuddy / qoder / trae 用 `off`，zcode 用 `none`。**

值取 `none` 而不是别的：它是 zcode 自己报出来的合法词汇里的**唯一**「关」
（`minimal` 起就是开了），且与 `off` 语义相同 —— 实测两者在别处等效
（`wb` 侧 `off` 与 `none` 都是 0 个思考 token）。

### 声明是**逐模型**的，所以按渠道给是正当用法

原先 `route-registry.ts` 里写的是「整份清单共用一个对象」，前提是「档位不分渠道」。
**实测推翻了这个前提**，于是回查宿主：`dsh-llm-pi-ai` 的
`resolveModelReasoning(provider, entry, base)` 读的是 **`entry.reasoningEfforts`** ——
**逐模型条目**，不是整份 provider。

所以这里改成**逐行按各自渠道给**，比「按渠道」还细一层，且**不必拆 provider**。

⚠️ 注意它**不影响界面**：档位**名**（键）永远是 `off` / `high`，
只有发出去的**值**按渠道变 —— 用户看到的仍是「关」与「开」两个选项。

### 实测证据（2026-10-06）

`zcode/glm-5.2`，每个档位重复 3 次：

| `reasoning_effort` | 结果                                            |
| ------------------ | ----------------------------------------------- |
| `off`              | **3/3 被 `1210` 拒**（参数校验先于模型校验）    |
| `none`             | 3/3 通过参数校验，落到 `3006 model not allowed` |
| `high`             | 同上                                            |

另外 `zcode/glm-5.3` **九个档位全部 200**（它可调用），也照样接受 `none`。

⚠️ **`1210` 是 zcode 独有的**：裸名 `glm-5` / `glm-5-turbo` / `glm-4.5-air` 的 400
是 `3006 model not allowed`（模型不可用，与档位无关），**不要混为一谈**。

## 替代方案（强制）

- **zcode 干脆不声明档位**：回查宿主后这条**不再成立** —— 声明是**逐模型**的
  （`entry.reasoningEfforts`），所以「只给 zcode 不声明」理论上做得到。
  ⚠️ 但它**修不了这个 bug**：zcode 崩的原因是「值写错」，不是「不该有档位」；
  不声明等于把 zcode 的档位这一栏整个拿掉，用户连「开」都选不了 —— 那是**功能倒退**。
  真要「按渠道去掉档位」是另一件事（`AGENTS.md` 待办「`providerId` 粒度裁决」）。
- **全局把 `off` 改成 `none`**：能修 zcode，但**改了其余三个渠道的行为** ——
  它们实测接受 `off` 且等效，为一个渠道动全部渠道的请求参数，收益为零、风险非零。
- **给 zcode 多声明一个 `off` 键、值写 `none`**：档位名与值可以不同，看起来更「统一」，
  但**用户看到的仍是「关」这一个选项**，徒增一层间接；按渠道给值已经够表达。
- **不修，只记进报告**：那是上一轮的处置（`docs/reasoning-effort-audit.md`）。
  但这条不同于「假旋钮」——它是**硬错误，会让整轮对话失败**，属真缺陷，不能只记不修。

## 影响

⚠️ **超集是安全的，缺项不是**：宿主校验的是「声明形状」（非空、除 `off` 外至少一个、
值非空串），**不校验值是不是上游认的词** —— 所以写错**只会到请求时才炸**，
而且炸的是**整轮对话**。这就是为什么这个值必须由实测决定、不能猜。

代价与边界：

- 拼写差异登记在 `model-caps.ts` 的 `OFF_SPELLING`（**一处**）。将来某渠道换词，
  加一行即可 —— 判据会逼着每个渠道都有值。
- `none` 在 zcode 上确认能过**参数校验**；但 zcode 多数模型本身不可调用（`3006`），
  所以「关掉思考」这件事在 zcode 上**目前只有 `glm-5.3` 能真正验到**。
  等 zcode 的凭据 / 区域问题解决后应复验。

判据：`tests/model-reasoning.test.ts` —— 形状契约 + **逐渠道都要给出「关」的拼写**
（落空就会退回一个上游不认的词）。
