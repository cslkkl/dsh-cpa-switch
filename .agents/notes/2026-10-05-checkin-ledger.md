# 决策：今日签到账本 —— 本机记「今天签过」，补上游没说那一格（2026-10-05）

状态：生效

## 问题

维护者实机反馈：**今天明明已经签到了，刷新或重进面板后卡片上却没有「已签到」
标签**，非得再点一次签到才显示 —— 而那一次**已经领不到积分**（今天确实签过）。

排查方向一开始被引到「是不是没存缓存」，实测后发现**恰好相反**：缓存太多了。

### 实测：四层缓存，各活多久

| 层                 | 存什么                          | 寿命                                   | 怎么被观察到            |
| ------------------ | ------------------------------- | -------------------------------------- | ----------------------- |
| **上游 CPA**       | `credits`（**签到态随它回来**） | 自己定；实测 `fetched_at` 冻结 ≥3 分钟 | **点签到才刷新** ← 根因 |
| 宿主 `CpaCache`    | 账号 + 余额                     | 5 秒，写操作立即失效                   | 基本无感                |
| 浏览器 `ReadCache` | 同上                            | 30 秒 fresh / 300 秒 stale             | 切页签秒开              |
| 页面刷新           | ——                              | **全清**（纯内存 `Map`）               | 刷新后必读上游          |

关键证据：反复读 `trae /accounts` 三次，`credits.fetched_at` **恒为
`15:52:43`**，而同一时刻 `server_time` 在推进（15:55:32 → 15:55:36）。
**上游自己把签到状态和余额一起缓存了**，只有写操作才推动它刷新。

于是链条是：

1. 今天签过了（或有开机补签替你签了）；
2. 上游那份缓存里的 `checked_in` 还是旧的 → 界面显示成「没签到」；
3. 用户再点一次签到 → 写操作 → 上游刷新 → 标签才出现；
4. 但这次**领不到积分**，因为今天确实签过了 —— 这是**正确**的结果，不是失败。

## 决策

**签到是按天、不可逆的事实，所以本机记一份。**

新增 `src/checkin-ledger.ts`（纯函数）+ 复用既有的
`$DSH_HOME/storages/cpa-panel-checkin.json`：

- **记录时机**：单号/渠道级签到**成功**后，以及**开机补签成功**后；
- **记录粒度**：`渠道 → authIndex → 日期串`。值存**日期**而不是布尔 ——
  查的时候比一下 `localDay()` 就自动作废，不需要「谁负责重置」这种清理逻辑；
- **应用时机**：账号域的 `loadAccounts` 组装账号时，把账本叠到上游报的
  签到状态上；
- **只补不覆盖**：

  | 上游给的              | 账本说今天签过 | 结果                          |
  | --------------------- | -------------- | ----------------------------- |
  | `checkedToday: true`  | 有/无          | `true`（上游权威）            |
  | `checkedToday: false` | 有             | `false`（**上游权威**）       |
  | 没有签到块            | **有**         | **`true`** ← 唯一用武之地     |
  | 没有签到块            | 无             | `undefined`（维持「不知道」） |

- **渠道级签到**（不带 `authIndex` ＝ 签该渠道全部账号）记在保留键 `''` 上，
  读的时候**账号键与渠道级键都查** —— 那一刻我们并不知道渠道里有哪些账号。
- **判定是「任一键是今天」，不是「优先那个键是今天」**（2026-10-06 修正，
  见下「修正：优先级只用于取值」）。

### 修正：优先级只用于取值（2026-10-06）

上线一天后实机踩到：**qoder 开机补签成功，卡片上却什么都没有**。

根因是「账号级优先」被写成了**取值与判定同一句**：

```ts
byAccount[authIndex] ?? byAccount[CHANNEL_WIDE] // 旧写法
```

开机补签只写**渠道级**（那一刻不知道渠道里有哪些号），而该号的**账号级**键
还留着**昨天**的日期。`'2026-10-05' ?? …` 不会回退 —— 昨天那条把今天那条挡掉，
`isRecordedToday` 判 false，`applyLedger` 于是返回 `undefined`（＝「不知道」），
界面**整行没有签到标签**。qoder 的签到状态**只**来自账本（它的 `parseCheckin`
恒为 `undefined`，没有第二条数据源），所以在下次「按号签到」写进账号级键之前，
**刷新多少次都不会出现**。

实测证据（`$DSH_HOME/storages/cpa-panel-checkin.json` 两次快照）：

| 时刻                 | `qoder` 下的键                              | 界面             |
| -------------------- | ------------------------------------------- | ---------------- |
| 开机补签后           | `'' = 2026-10-06`、`dc03aa7d… = 2026-10-05` | 无标签（旧写法） |
| 又点了一次单卡签到后 | `'' = 2026-10-06`、`dc03aa7d… = 2026-10-06` | 出现「已签到」   |

同一份文件里还有天然对照：`workbuddy` 只有渠道级键 → 正常显示；
`trae` 两个号都有当天的账号级键 → 正常显示。

修正后的语义：**两条键各自独立地回答「本机有没有说过这个号今天签过」，
任一命中即成立**。账号级优先**只用于取值**（哪个日期串代表这个号，诊断用），
不参与判定 —— 判定问的是「说过没有」，不是「最新那条是哪天」。

⚠️ 这条修正**不动「只补不覆盖」**：上游说 `false` 时账本仍然不翻成 `true`。
改的是「哪一天」，不是「谁说了算」。

## 替代方案（强制）

- **「刷新」时顺带打一次各渠道的 refresh 动作**：能推动上游重取，但
  (a) 把「看数据」变成「触发写操作」，刷新语义被污染；
  (b) 上游若因风控限频，频繁 refresh 有代价；
  (c) **治不了根本**——用户不开面板的那些时段，上游缓存照样是旧的，
  下次打开又是一样的现象。账本按天记事实，与上游刷不刷新无关。
- **界面显示「上次已知状态」并标注时间**：把不确定性转嫁给用户，
  而「今天签过」这件事**本来就没有不确定性** —— 它就是事实。
- **把上游缓存 TTL 调短 / 每次强制 bypass**：上游是独立进程，插件只能调它的
  接口（[架构说明](../../docs/ARCHITECTURE.md)），没有这个旋钮。
- **用「上次签到操作成功」的布尔记忆**：跨天不会失效，第二天会显示成
  「已签到」而实际没签 —— **比不显示更糟**。所以账本存日期、按天比对。
- **把「没有签到块」直接当成「未签到」显示**：会撒谎。上游不给禁用账号的
  签到块（实测），猜「未签到」等于凭空报一个上游没说的状态。
- **（2026-10-06 追加）把账号级键的 `??` 短路当成「哪条更新用哪条」**：
  它看起来只是「优先」，实际**否决**了渠道级键已经说过的今天。
  改成「任一键是今天」即可，不需要引入「哪个键更权威」的新概念。

## 影响

**收益**：签到过的号**当天一直显示「已签到」**，不再受上游缓存影响；
用户不会再「为了看到标签」而重复点签到（那一次确实是白点）。

**代价 / 边界**：

- 账本是**本机记录**，只认本机做过的签到。别的设备/CPA 控制台签的，本机不知道
  —— 那种情况仍以上游回报为准。
- 账本损坏时**安全降级**为空账本（`readCheckinLedger` 吞错并逐字段校验），
  退回「不知道」，不会因为辅助记录坏掉就读不出账号。
- **不覆盖**上游的 `false`：上游能重新判定（如风控撤销签到）。

**仍未解决**（另案）：上游**不给已禁用账号的签到块**（实测）。
CPA 的签到是**按渠道签全部账号含已禁用的**，所以那个号其实也签了，
但状态上游不上报 → 它的标签行永远是空的。这是**信息缺口**，
按「不猜」原则保持现状（维护者 2026-10-05 确认）。
