# 决策：汇总三格在额度读不到时照画并说明（2026-10-07）

状态：生效

## 问题

真机反馈：workbuddy 渠道顶上那三格（剩余 / 已用 / 额度池）**整个消失** ——
「一开始加载的时候骨架还有的，加载好之后就没了，而且没看到数据」，
但账号卡片照旧显示。别的渠道正常。

原先的渲染条件是一行：

```ts
const showSummary = capabilities.credits && accounts.some((a) => a.credits !== null)
```

拆开是两个判断挤在一个条件里：

| 问题                           | 当时的依据                        |
| ------------------------------ | --------------------------------- |
| 这个渠道**有没有额度**这个概念 | `capabilities.credits`            |
| 这一轮**读没读到**额度         | `accounts.some(credits !== null)` |

后果是**「读不到」与「本来就没这三格」在界面上长得一模一样**：一个额度都没读到时
整块不渲染，用户看到的是骨架消失后一片空白 —— 判定成「面板坏了」。
而**没有任何报错**。

根因是**归属没定**：`capabilities.credits` 是渠道的**静态能力**，
`credits === null` 是**这一次读的结果**。拿后者当前者的门，就把
「暂时读不到」升格成了「这个渠道没有这个东西」。

⚠️ 还有同一类问题的另一半：合计只累加读到的账号（`sumCredits`），
所以**丢一个号**时那三格会显示一个**偏小却看起来正常的数** —— 比整块消失更危险，
因为它看起来是对的。

## 决策

**「有没有这个能力」与「读没读到」分开判；缺数据仍占位；读不到就说一句。**

判定收进纯函数 [`summary-hint.ts`](../../src/client/summary-hint.ts)，接线在
[`PluginPanel.tsx`](../../src/client/PluginPanel.tsx)：

| 情形                     | 三格             | 那句话                                      |
| ------------------------ | ---------------- | ------------------------------------------- |
| 渠道没有额度能力         | 不画             | 不说                                        |
| 加载中                   | 不画（骨架占位） | 不说                                        |
| 整个列表读失败           | 不画             | 不说（`.failed` 已在说）                    |
| 0 个账号                 | 不画             | 不说（`empty-hint` 已在说）                 |
| 有账号、全读到           | **画**           | 不说                                        |
| 有账号、**一个都没读到** | **画（`—`）**    | 说「额度读不到 + 点刷新重试」               |
| 有账号、**只丢了一部分** | **画**           | 说「有 N 个账号的额度读不到，合计不含它们」 |

三条纪律：

- **顺序即语义** —— `hasCredits` / `loading` / `error` / 0 个账号 都必须排在
  「有没有读到额度」**之前**。读失败时账号数必然是 0、额度必然为空，
  先看额度就会把「读不到」说成「这个渠道没额度」（与 `empty-hint` 的
  「读失败不许说没有」同一条口径）。
- **缺数据仍要占位**（填 `—`）—— 不画会让切渠道时上面缺一块，
  这正是架构 F40 已经定过的规矩；本决策是**把实现拉回它**，不是新发明。
- **不说原因** —— 网络 / 凭据 / 上游抖动都可能。上游其实在逐账号的 `error`
  字段里写明了原因，但本仓**没有把它传上来**（见下「未做」），
  所以现在只能说「读不到 + 怎么办」。

## 替代方案

- **保持「读到才画」**：就是本次要修的那个静默 —— 用户只能靠猜。
- **整块换成一个提示**（三格不画、只留一句）：省空间，但好在坏两态之间
  **布局会跳**，且丢掉「缺的是哪三个数」这个信息。与 F40 的「占位」相悖。
- **把读不到的号在合计里按 0 算**：直接造假数，与「缺数不填 0」冲突。
- **列一句「部分账号读不到」但不改渲染**：解决不了「整块消失」这个主诉。
- **复用 `.notice`**（状态条下方那条 3px 严重度边条的横幅）：那个角色是
  **站着的故障**（端口被占、配置代际不符），有边框与底色；这里是数据区里的一句说明，
  与 `.empty` 同一角色。共用会让「同一位置时而是横幅、时而是句子」。

## 影响

- 收益：三格**不再凭空消失**；额度不全时用户知道合计不完整（不再有无声的偏小值）。
- 代价：读不到额度时会多出两行字；三格显示 `—` 而非整块留白。
- **未做（明确记下）**：把上游逐账号的 `error` 传上来，让提示说出**真实原因**。
  那要改 `ChannelSpec.parseCredits` 的返回形状（四个渠道 + 契约），
  属结构改动，按「先补判据再动结构」另立项。
- 判据：[`tests/summary-hint.test.ts`](../../tests/summary-hint.test.ts)
  —— 逐条钉住「什么时候说、什么时候**必须闭嘴**」，含「改回旧写法会红」的自证。
