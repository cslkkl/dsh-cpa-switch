# 决策：启动不等读，用磁盘缓存兜住（2026-10-06）

状态：生效

## 问题

重启后选择器**一直**显示 `CPA · Doubao-Seed-2.1-Turbo`，点一下（**两秒内**）
才变成 `Trae · …`。不是「过渡态自愈」——是**插件在启动时推了半成品**。

### 时序实测把两件事分开了

之前把「54 秒」当成 CPA 起不来，那是**误读**。实测：

| 量                      | 值                    |
| ----------------------- | --------------------- |
| DSH 进程 → CPA 进程启动 | **7.6 秒**（不是 54） |
| `/v1/models` 单次读     | **2–4ms**             |
| `auth-files`            | 61–75ms               |
| 逐凭据（6 个，并发）    | 372–398ms             |
| 供给面一轮              | **127–151ms**         |

**关键（源码依据）**：`/v1/models` 读的是**内存注册表**
（`GetAvailableModels` → `availableModelsCache`，`model_registry.go:1276`），
而注册表的内容有**两个来源**：

1. **远端目录** —— `StartModelsUpdater` 一启动就去抓（`model_updater.go:88`），**与凭据无关**；
2. **凭据注册** —— `RegisterClient`（`model_registry.go:434`），凭据加载完才有。

所以**端口一通 `/v1/models` 就已经有内容，而供给面还空着** →
归属算不出来 → 落 `CPA ·` 兜底名。

「点一下两秒就好」正好对上：那时凭据早加载完了，而供给面一轮只要 ~140ms。

### 为什么「等」解决不了

判据需要回答「供给面加载完了吗」，但
**「还在长」与「永远长不出来」在时间上不可区分** ——
给短了会把半成品当成品（旧 bug），给长了会把坏渠道等到超时（新 bug）。
上一批试过「连续两轮指纹相同」+ 两个预算，仍然卡在这个点上。

## 决策

**不再判断「供给面好了没」，改成「启动就不等」。**

上次**完整**成功过的清单写盘；启动时**先把它推上去**（零读、立即可用），
再后台读新的：读全 → 更新 + 写盘；读不全 → 保持旧的。

这把「就绪」从一个**时序判断**变成了**状态判断** —— 用户永远不必等，
也就永远看不到半成品。

### 三条约束（维护者定，都有判据）

1. **不设硬过期** —— 过期后又会走回「等读 → 半成品 → `CPA ·`」，
   等于把刚修好的症状请回来。偏旧由「读全后覆盖」自然解决，
   不由计时器决定「什么时候没有数据可用」。
2. **宁可少显示，不可显示已删除的模型** —— 落点是**写盘前的形状校验**：
   空清单 / 形状不对 / 版本不符，宁可没有缓存，也不要坏缓存。
3. **`port` 变了作废** —— 清单里的 `baseURL` 焊死了端口。

### 实现要点

- **缓存放 `state.ts`**（不新建模块）：它已经是「跨进程状态」的唯一登记处，
  且与签到账本同构（记住上次成功的、补本次空缺）。新建模块会重复
  路径、读写吞错、单入口三件事。
- **校验住在 `route-registry`**（不在 `state.ts`）：「可信吗」依赖
  `RouteProfile` 的形状（`baseURL` 的 port、`models` 非空），那是路由域的语义。
- **`lastGood` 变成磁盘缓存的运行时镜像** —— 于是「重载回推什么」与
  「下次启动用什么」是**同一份数据、同一个赋值点**，半成品进不来。
- **快路径收进 `refresh`**，`boot` 与 `config-reload` 共用一套
  （原先 `config-reload` 单独写了一份，给 boot 加时极易只改一处）。
- **写缓存只在「读全 + 没跳过任何渠道」时**：跳过意味着清单少一块，
  缓存下来下次启动会**未经任何读**推给用户，没有东西能纠正它。

## 替代方案（强制）

- **判断供给面是否稳定后再推**（上一批的做法）：根子上的难处是
  「还在长」与「永远长不出来」不可区分。实测试过「连续两轮指纹相同」——
  卡死的供给面**也满足**它，于是又把半成品推了出去。**否决**。
- **首轮门不通过就 etc.（等更久）**：只是把窗口挪长，
  且 CPA 起不来时会等到上限才给用户任何东西。**否决**。
- **缓存设 TTL**：见约束 1。**否决**。
- **把缓存写进 `lastGood` 的赋值处（`pushProfile`）**：那个函数
  **快路径与 degrade 也会调**，会把「上一份」反复写回去。**否决**，改为在
  「读全 + 无跳过」的显式位置写。
- **跳过渠道时也写缓存**：那份清单少一个渠道、同名模型可能已退化成裸名，
  缓存下来下次启动直接推给用户。**否决**（约束 2）。
- **品牌类型强制「只有就绪快照能写盘」**：类型能拦正常写法，
  但拦不住 `as` 强转，而**运行时校验本来就要做**（形状来自磁盘、不可信）。
  两道都要，但类型不是唯一防线 —— 记在判据里更实在。**未采纳为唯一手段**。

## 影响

- **收益**：启动**立即**有清单，用户不必等；半成品不再可能被推出去
  （门 + 只写完整快照，两道）。
- **代价**：多一个状态文件（`cpa-panel-routes.json`）；缓存可能偏旧
  （上次的账号集合），由读全后的更新覆盖 —— 期间用户可能选到刚失效的模型，
  表现为一次 4xx，比「看到错归属」轻。
- **判据**：`tests/state.test.ts` 9 条 + `tests/route-registry.test.ts` 8 条。
  **三条约束各自独立变异验证过**：
  - 去掉「跳过渠道不写缓存」→「跳过永久坏渠道时也不写缓存」**恰好一条**转红
    （⚠️ 这条判据是变异验证**发现缺失后补的** —— 原先 53 条全绿，护栏等于裸奔）；
  - 去掉端口校验 →「端口变了不认缓存」转红；
  - 加一条 60 秒 TTL →「不设硬过期」两条转红。
- **真机验收**：需重启 DSH。**攒批**（与 Trae 窗口等其他需重启改动一起验）。

## 相关（本篇的前因）

⚠️ **本篇是[统一「就绪」判据](2026-10-06-unified-readiness-gate.md)的直接延续**，
不是并列决策 —— 两者构成一条**因果链**：

|                                                      |                                                              |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| [就绪判据那篇](2026-10-06-unified-readiness-gate.md) | 供给面没读全就**不推**（此前会推出半成品，显示 `CPA · xxx`） |
| **本篇**                                             | 门变严 → **首次启动推不出东西** → 用磁盘缓存兜住             |

**换句话说：没有前一篇就不会有本篇要解决的问题。**

⚠️ 但**这不是回归**：前一篇之后的表现是「什么都不推」，
它**不会给出错归属**；而 `CPA · xxx` 是谎称那些模型属于 CPA ——
两者都坏，后者更容易让人按它得出错误结论。

## ⚠️ 本篇没解决的那一半（**已于 2026-10-07 收口**）

缓存只对**有历史**的情况生效。**首次启动**（缓存文件还不存在）时：

- 不点**不会自愈** —— 一直是 `CPA · xxx`，点一下才写盘；
- 点完之后的**第二次重启**才立即正确。

机制：`refresh` 是**读一次就收场**的，没有「过一会儿再读一次」。

⚠️ **这一半现在修掉了**，见[目录护栏 + 有限重读](2026-10-07-catalog-shrink-guard.md)：

- **有限重读**（`boot` / `setup` / `oauth` 触发，`2/5/15/30s`，四次封顶）
  补上了「过一会儿再读一次」；
- 写盘判据从「**非空**」升级成「**不比上一份差**」—— 残缺目录不再可能进缓存。

⚠️ **症状表述已被 2026-10-07 的改动更新，但这条边界本身曾长期存在**：
`CPA · xxx` 兜底已从代码里删除，所以首次读不全当时表现为
**「模型数量偏少」**而不是「名字挂错渠道」。第 1 批真机三次重启里中两次
（只剩 1 条模型 / 只剩一个渠道），几秒后或点一下才自愈 —— 正是本篇这条边界
加上「残缺被当完整写盘」共同造成的。

本篇的三条约束（**不设硬过期** / **只有完整快照才写盘** / **`port` 变了作废**）
**一个字都没改**，护栏是加在「完整快照」判据之前的一道闸。
