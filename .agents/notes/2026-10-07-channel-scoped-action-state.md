# 决策：渠道级动作状态按渠道分槽（2026-10-07）

状态：生效

## 问题

真机反馈（维护者）：**在 A 渠道点「全部签到」，切到 B 再切回来，提示没了、按钮也不「忙」了。**

顺着看下去，症状比「丢提示」更重，而且**两个都不报错**：

| 现象                     | 机制                                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 切走再切回，按钮又能点了 | `plugin` 一变就把 `busy` 清成「没在飞」，而请求还在路上 —— 再点一次就是**重复签到 / 重复跑任务**                                                        |
| 提示报在**别的页签**上   | 清空只发生在**切换那一刻**；A 的结果在那之后才回来，`setToast` 打在共享状态上，于是它被当成 B 的结果显示出来（文案说「签到 4 个账号」，而用户正看着 B） |

根因是**归属**没定：这两个状态属于「发起它的渠道」，却被当成「当前显示的页签」的。

这条与「切渠道不闪」是同一笔账的两面。当初为了不闪，`Panel` 去掉了
`key={activeMeta.id}`（不重挂载，见[决策记录](2026-10-04-channel-switch-read-strategy.md)），
代价是「跨渠道的状态必须自己认领归属」—— `use-resource.ts` 的 `held` / `heldError`
都带 key 认领了，而动作状态走的是「清空」。

## 决策

**判据与分槽都进纯函数 `src/client/channel-action-state.ts`，hook 只接线。**

四个状态（`busy` / `cardBusy` / `toast` / `autoOverride`）收在一个按渠道分槽的对象里：

- 读一律经 `viewOf(state, plugin)` —— **只认自己那一格**，别的渠道的提示读不到；
- 写一律经 `markBusy` / `markCardBusy` / `showToast` / `setAuto`，只替换目标那一格，
  且返回新对象（就地改会让「先记 A 再记 B」把 A 一起改掉）；
- **删掉**那个 `[plugin]` 的清理 effect。

`report` 因此**绑定到当时的 `plugin`**：卡片在 A 那次渲染里拿到的 `onReport` 就是绑定 A
的那个闭包，切走之后 A 的结果回来，走的正是当初那个闭包 —— 结果自然落在 A 名下。
`runAll` / `toggleAuto` 同理（它们本来就捕获 `plugin`）。

乐观覆盖层的「后端确认才自我删除」也一并收进纯函数（`reconcileAuto`），
且**无事可做时返回同一个引用** —— 调用方是在 effect 里 `setState`，
返回新引用会让那个 effect 每轮都重渲染。

## 替代方案（强制）

- **保留清空，只是把「在飞」单独放出来**：仍会「结果串门」—— 清空管不住**切换之后**
  才回来的那个响应，而那正是提示报错页签的原因。只修一半。
- **把状态提升到 `Panel`（父级）**：`toast` 与 `busy` 会与「哪个渠道」脱钩，
  报在别的页签上的问题原样存在，只是换了个位置。真要在父级做，就得把渠道也一起传上去
  —— 那与「分槽」是同一件事，只是住在更远的地方。
- **给结果加「过期时间」，超过 N 秒就不显示**：切走期间到达的结果会被丢掉。
  用户刚发起过动作，回来时正需要那条结果；而「多久算太久」没有可信判据，
  加阈值等于给一个假的确信。**不做**（分槽之后提示只在切回来时显示，没有过期问题）。
- **阻止在飞时切渠道**：把用户的导航拿来换实现方便，体验上是倒退。
- **`useResource` 的 `pending` / `seq` 一并按 key 认领**：它们确实同样没认领 ——
  `seq` 是**单个 ref**、跨 key 共用，于是「切渠道」与「上一个渠道的动作完成」两次读重叠时，
  先发的那次会在 `mine !== seq.current` 那一行**提前出局**，而那个 return 位于
  `setPending(false)` **之前**：它既没写下 `held`、也没清 `pending`。
  **不属本次**：症状不同（是「那个渠道只剩缓存里那份值」而不是提示串门）、
  影响面更大（每个读路径都经它），而且**具体症状与时序相关，本次没有实测出来** ——
  要动得先把症状钉住，另立一轮。

## 影响

**收益**：

- 在飞状态跟着渠道走 —— 切回来按钮**仍然**是禁用的，那一次重复点击没有了；
- 结果落在发起它的渠道上 —— 不再报在别的页签上，而且**切回来还能看到**（原先是被清掉）。

**代价**：

- 切走期间到达的结果会**留着**，用户切回那个渠道时才看到。刻意如此（见替代方案第三条）。
- 提示不再受「切换即清空」兜底，所以**必须**由分槽保证不串门 ——
  判据是 `tests/channel-action-state.test.ts`（18 例），守卫是
  `tests/client-cache-keys.test.ts` 里「不许有以 `plugin` 为唯一依赖的 effect」那一条。
- `client-cache-keys.test.ts` 原先用**抓源码文本**钉着旧机制（找
  `serverAutoCheckin === autoOverride` 那段）。判定搬进纯函数后判据也搬过去，
  那里只剩接线断言 —— 抓文本的守卫换个写法就红、判定写错却照样绿。

## 复验

真机路径：在 workbuddy 点「全部签到」（号多时要几秒）→ 立刻切到 trae → 等到
workbuddy 那次完成 → 观察两件事：trae 上**不出现** workbuddy 的提示；切回 workbuddy
能看到那条提示，且在飞期间按钮一直是禁用的。

浏览器半端改动，`pnpm build` 后**刷新页面**即可（宿主半端不随刷新加载）。
