# 决策：PR 与合并的纪律（正文六段、逐提交评论、rebase merge 与合并后回填 sha）（2026-10-05）

状态：生效

## 问题

维护工作里最容易**烂在半路**的不是代码，是 PR 上的记录：一个批次七八个提交，
评审要能逐条对照「这一步改了什么、验了什么」；而正文与评论是**长期留档**的，
链接写错就是永久 404、sha 写错就再也对不上 `main`。

已实踩三次：

- 正文里的**相对链接**被 GitHub 解析到 `.../compare/<path>` 这个**空视图**，点开什么都没有；
- 写成 `blob/<功能分支>` 的链接，在分支合并删除后**永久 404**（P5a 的正文里有六处，
  合并前逐个 PATCH 回 `main`）；
- `gh pr comment --body` **内联**中文 markdown：PowerShell 把反引号当转义符，
  四条已发评论成了 `\`sha\`` 这种乱码，只能逐个 PATCH 修回。

## 决策

**正文固定六段**：目的 / 边界变化（引用方案编号）/ 提交清单 / 验收证据 / 回滚方式 /
关联决策记录 —— 评审者按这六段就能判断「该不该合」与「合错了怎么退」。

**每推一个提交追加一条评论**：`<sha> <subject>` + 该步验收结果摘要（三行内）。
批次收尾再补两条清单评论：**真机项**（写成 `- [ ]`，合并前勾掉）与**合并前最后确认**
（CI 绿 / 文档同步 / 链接与行尾校验 / 决策记录 / 版本策略）。

**文本一律走文件**：`--body-file` 或 `-F body=@文件`，**不内联**进命令行。

**链接写绝对 URL，且 ref 用 `main`**：`https://github.com/<owner>/<repo>/blob/main/<path>`。
⚠️ **仓库内部的文档照旧用相对路径** —— 那是文件里的链接，与页面里的不是一回事。

**标签**：每个 PR 打 `boundary-refactor` + 类型标签；**打之前先跑 `gh label list`**，
不凭记忆（标签集由维护者在仓库设置里维护，改过名之后旧名直接贴不上去）。

**合并**：rebase merge（保住每个原子提交，不用 squash）→ 删分支 →
`git switch main && git pull --ff-only`。回滚靠 `git revert <sha>`（线性历史，逐个可退）。

**合并后回填 sha**：GitHub 的 rebase merge **会重写提交**（即使能快进也重写），
于是逐提交评论里的 sha 在合并后指向**已删分支上的孤儿提交**。合并后按 subject
一一对应（本批 8/8 用 subject 断言校验过）把正文与评论 PATCH 成 `main` 上的新 sha，
并留一行说明。

## 替代方案（强制）

- **squash merge**：历史干净，但丢掉原子提交 —— 「每个提交单独能回滚」这个性质没了，
  而批次纪律正建立在它上面（回滚粒度 = 一次判据修正）。
- **merge commit**：保住提交，但历史出现分叉，`git log --oneline` 不再能当批次清单读。
- **评论正文内联写**：省一次写文件，代价是反引号被 PowerShell 吃掉 —— 已实踩。
- **链接写相对路径**：GitHub 解析到 `.../compare/<path>` 空视图 —— 已实踩。
- **链接写功能分支名**：分支合并即删，链接永久 404 —— 已实踩（六处）。
- **不写逐提交评论**：一张提交表就够 —— 但「这一步验了什么」只能靠 `git show` 反推，
  而真机验收结论**不在代码里**。
- **合并后不回填 sha**：评论里的 sha 在 GitHub 上仍能点（指向 PR 的旧 head），
  但在 `main` 上**找不到对应提交**；回头核对八次就要重新对八次 subject。
- **正文只写「改了什么」**：不写**边界变化**与**回滚方式**，评审者就得自己去 diff 里
  推断哪条边界动了 —— 而边界变化恰恰是本仓最需要评审的部分。

## 影响

- 一个批次的 PR 读完 = 六段正文 + N 条逐提交评论 + 两条清单评论；评审与回滚都能就地下手。
- 代价：每批次要多写十来个小文件；本批已用脚本一次生成（文本仍逐条写过、逐条读过）。
- **未解决**：rebase merge 必然重写 sha，所以「评论里的 sha 与 `main` 一致」**只能靠
  合并后回填**这一步维持。若将来打开 auto-merge 或换成别的执行者，这一步最容易漏 ——
  判据是 `git log --reverse --format='%h|%s' origin/main -N` 与评论里的 sha 逐条对齐。
