# 决策：思考档位只暴露两档（off / high）（2026-10-06）

状态：生效

## 问题

用户要「像官方 DeepSeek 那样能选推理档位」，但 CPA 的模型选择器里**根本没有
Effort 那一行**。根因不在 CPA：渠道插件返回的模型清单**只有 `id` 与 `name`**
（实测 `/v0/management/plugins/workbuddy/models/groups`），没有能力字段，所以宿主
认为这些模型不支持推理，连选的地方都不显示。

而底层其实是通的：直接给 CPA 发 `reasoning_effort`，它会返回 `reasoning_content`
（实测 `wb/deepseek-v4.1-flash` 稳定返回 30–66 字）。缺的只是「**声明**」这一环。

宿主认的字段是 **`reasoningEfforts`**（`dsh-llm-pi-ai` 的 `resolveModelReasoning`），
形状是「档位名 → 发出去的拼写」，例如 `{ off: 'off', high: 'high' }`。

## 决策

**只暴露两个档位：`off`（关）与 `high`（开）。** 默认开启，面板给一个总开关能整体关掉。

### 为什么不是一整套刻度

实测（`wb/deepseek-v4.1-flash`，每档各 10 次，同一道需要真推理的题）：

| 档位           | 思考 token 均值                 | 标准差 |
| -------------- | ------------------------------- | ------ |
| `off` / `none` | **0**（合计 20 次全 0，无例外） | 0      |
| `low`          | 1003                            | 276    |
| `high`         | 1044                            | 249    |
| `max`          | 1213                            | 296    |

- **「关」是硬的** —— 恒为 0，唯一经得起复验的值；
- 中间档位的差异**够不着显著**（t = 0.35 / 1.39 / 1.64，一般要 ≥2），
  而**同一档位内部的波动（±280）比档位之间的差（±200）还大**；
- 所以「低/中/高/最大」这种刻度是在**制造错误预期**：用户选 `max` 未必比 `high` 想得多。

⚠️ **这是本仓替用户做的判断，不是上游的契约。** 上游**接受**一整套词汇
（`minimal`/`low`/`medium`/`high`/`xhigh`/`max` 实测都收下并返回 200），
**但收下不等于会照做**。既然测不出差别，就不给用户一个假旋钮。

### 为什么不是「逐模型实测后声明」

workbuddy-bridge 那类插件能做「点按钮检测档位」，是因为它**自己发请求**（直连官方
接口）。我们的请求路径是 `DSH → CPA → 上游`，**插件插不进手** —— 声明只能写死在
清单里。而且它的 README 自己也写明：检测结果只表示「上游当前接受该档位」，
**不承诺它改变推理行为**（与上表同源）。

### 为什么默认开、以及开关的真实作用

默认 `true`：让 Effort 行出现、思考过程看得见，这是用户要的东西。

⚠️ **开关的首要价值不是「给不想用的人关掉」，而是逃生通道**：

上游可能对档位值返**硬错误**并让整轮会话失败（2026-10-06 实踩
`11150 the reasoning effort value is not supported by the current model`，
`503 auth_unavailable` / `400` 两种外壳都出现过）。默认全开 = **每个请求都带档位**，
所以抽风时影响面比以前大；关掉开关即回到「不声明」，是唯一的即时恢复手段。

## 硬约束（写错不是「这模型没档位」，是全部模型消失）

`reasoningEfforts` 的形状由宿主校验，违约会让**整个 `provider` 注册失败**：

- 空对象 → `declared an empty reasoningEfforts`；
- 除 `off` 外没有别的档位 → `offers no level beyond "off"`；
- 除 `off` 外的档位值为空串 → `must not be an empty string`。

所以值**不由调用方拼装**，只由 `reasoningEffortsOf()` 返回一个常量；
判据 `tests/model-reasoning.test.ts` 把这三条与「只有两档」一起钉住。

## 替代方案

- **给全套刻度（`off`/`low`/`high`/`max`，与官方一致）**：用户最早的要求。
  放弃的理由是实测显示中间档位测不出差别 —— 给了就是**假选择**。
  代价是选择比官方少；但官方那套是官方适配器实现的，我们这条路的上游不保证照做。
- **直连上游（照抄 workbuddy-bridge）**：能自己检测，但代价是重写四个渠道的客户端、
  另建凭据体系，且**放弃 CPA 的多账号池**（13 个号、workbuddy 一家 7 个 ——
  额度叠加与容错正是 CPA 的价值）。**用一个次要功能换掉核心价值，不做。**
- **不做这个功能，只解决「看得见思考」**：可行且更保守，但没有解决用户
  「能选档位」的诉求，且开关本身就是逃生通道，留着有用。

## 实现位置

- `model-caps.ts` —— `REASONING_EFFORTS`（两档常量）+ `reasoningEffortsOf(开关)`；
- `config.ts` —— `reasoningEfforts` 布尔字段，默认 `true`；
- `route-registry.ts` —— 推清单时按开关给每个模型带上同一份声明（**现读**，不缓存）；
- `index.ts` —— 把开关以**函数**形式接进去（配置全 volatile，值随时会变）。

判据：`tests/model-reasoning.test.ts`（契约与硬约束）、
`tests/route-registry.test.ts` 的「思考档位声明」一节（声明真的落进清单 + 开关现读）。

## 已知边界（2026-10-06 全量实测，逐条见[实测报告](../../docs/audits/2026-10-06-reasoning-effort-off-vs-high.md)）

- **「关」不是所有模型都真能关掉**：99 个模型里只有 10 个（8 个在 workbuddy）是
  `off` 无思考 → `high` 有思考的**真开关**；**23 个方向相反**（`high` 比 `off` 想得更少），
  **9 个关不掉**，1 个（`hunyuan-chat`）两档都不思考。
- **`zcode` 的合法词汇里没有 `off`**：它的关闭语义是 `none`，选 `off` 会 400
  让整轮对话失败 —— 与「上游会对档位返硬错误」是同一条边界。
- **「关不掉的就把档位列删掉」在当前结构下做不到**：`reasoningEfforts` 是
  **provider 级**（按渠道）声明，要按模型区分必须先把 `providerId` 拆细，
  属结构改动 → 立项见 [docs/PLAN.md](../../docs/PLAN.md) §2.9。

⚠️ 这三条**不改变本文的决策**（仍只暴露 `off` / `high` 两档、默认开）：
它们说明的是「这两档在上游不一定被照做」，而**总开关的价值正在于此** ——
抽风时关掉它，即回到「不声明档位」。
