# 决策：「就绪」是一个统一判据（2026-10-06）

状态：生效

## 问题

模型路由的清单由**多份读**拼成，而它们**分开读、无同步**：

| 读                    | 自己的判据          | 它看不见什么                           |
| --------------------- | ------------------- | -------------------------------------- |
| `runtime.status()`    | `running`           | 没起来时整个清单为空（**症状 1**）     |
| `readStableCatalog()` | 条数连续两次一致    | 渠道供给面是不是空的（**症状 2**）     |
| `readChannelModels()` | 没抛错 → `complete` | 模型目录有没有跟上（**反向**同一个洞） |

三者**各自成功**、却互相矛盾时，推出去的清单就是「id 齐了、归属没齐」：
展示名的判据是 `plugin === undefined ? 'CPA' : channelLabel(plugin)`，
归属反查不到就落 `CPA` 兜底 —— 独供模型显示成 `CPA · custom_model_gemini`，
点一下（触发重算）才变成 `Trae · …`。**全程没有任何判据报错。**

两次症状（启动竞态、过渡态）是**同一个根**：没有东西回答
「这一轮读到的数据彼此对得上吗」。

## 决策

「就绪」的定义从**「每个读各自成功」**改成**「两份数据都在，且关系确定」**。

### 1. 读收在一处，由一条判据裁决

- `readReadySnapshot` —— **唯一的读入口**，产出 `ReadySnapshot`；
- `agreeOnOwnership` —— 「就绪」的**定义**：
  - 供给面为空 → **还没读到**（不确定）→ 等；
  - 供给面有内容而某 id 仍无归属 → ⛔ **这条已被取代**（2026-10-07）：
    认不出归属就**不产出行**，不再当成「第三方自带的事实」推出去。
    见[决策记录](2026-10-07-model-routes-managed-healthy-only.md) ——
    `CPA · xxx` 那是在**谎称** CPA 自有（它只是代理层），
    且与「这轮读丢了归属」完全同形。
    ⚠️ 供给面的口径也随之收窄：**只收托管渠道的可用凭据**。
- `readProfile`（会读 CPA）→ `buildProfileFrom`（**纯计算**）。
  **读全在一处，判断才可能一致** —— 这是本决策的核心，
  比任何单条判据都重要。

### 2. 「稳定」看内容，不看条数

`readStableCatalog` 原判据是「连续两次**计数**一致」，但计数相等**不等于**没变：
CPA 换凭据 / 刚加完号时，内容变了而条数恰好没变 ⇒ **陈旧目录被当成新事实**。

判据改为「**排序后的 id 集合**连续两次相同」。指纹排序后比较 ——
免得上游重排被误判成「还在变」而白等满预算。

### 3. 暂时 vs 永远必须分开

|          | 判据                  | 行为                                   |
| -------- | --------------------- | -------------------------------------- |
| **永久** | 404 / 401 / 403 / 410 | **跳过**该渠道、推其余；**不写别名段** |
| **暂时** | 超时 / 5xx / 连接被拒 | **等**（短预算退避）                   |

少了这条，**一个坏渠道就能把门永久卡死 → 全部模型消失**，比原症状更严重。

判据取「**宁可判成暂时**」：误判 permanent 会跳过**健康**渠道（模型变少），
误判 transient 只是多等一轮且有预算兜底 —— **代价不对称**。

跳过时**不写别名段**：别名段是**整段替换**，少一个渠道就写下去等于把 CPA 里
那些别名**删掉**。清单是自愈的（下轮补齐），别名是持久状态（删了要重写）。

### 4. 门不通过必须接上 `degrade`

有 `lastGood` → 回推它；没有 → 保持空。
**绝不孤立地「不通过就不推」** —— 那会让用户已选中的模型从选择器里消失。

## 替代方案（强制）

- **只修「两个目录同步」（不做内容稳定）**：那只堵住一个方向。
  计数相同而内容不同的陈旧目录照样通过 —— 第 3 个同类症状仍在 → 否决（本批两层一起做）。
- **`ownership-unsynced` 时直接放弃、不重试**：一刀切的另一个极端 ——
  第一次读永远早于供货面，于是**永远推不出清单**。实测：只改判据不重试，
  核心判据从「推错了」变成「什么都不推」，**两个都是 bug** → 否决。
- **给重试 120s 全额预算**：那是 `readStableCatalog`「等目录长齐」的量级
  （秒级到十几秒），而这里只等「另一份读追上」，量级是**一次往返**。
  实测给满 120s 会把「渠道一直读不到」从「立刻 degrade」拖成「等 5 秒」，
  拖垮 4 条既有判据 → 否决，改为短预算 750ms。
- **让 `readStableCatalog` 也去校验供给面**：把两份数据的耦合塞进一个「读目录」的函数，
  等于让底层知道上层的语义 → 否决，改由上层的 `agreeOnOwnership` 裁决。
- **永久失败的渠道也一起等**：等一万年也不会好，且会把门卡死 → 否决。
- **跳过坏渠道时也写别名段**：整段替换会把被跳过渠道的别名删掉 → 否决。

## 影响

- **代价**：稳定判定**最多**多等一轮（250ms 起）；「慢半拍」多等最多 750ms。
  换来的是「稳定」这个词真正等于「不再变了」。
- **收益**：第 3 个同类症状被堵在结构上 —— 不是「又补了一条判据」，
  而是**读只有一处、判断只有一条**。新增一份读时，它必然要进 `ReadySnapshot`，
  于是必然参与 `agreeOnOwnership` 的裁决。
- **判据**：`tests/route-registry.test.ts` 25 例。**两组变异各自独立**：
  - 短路 `agreeOnOwnership` 的供给面判据 → 「供给面未到时不许推」两条转红；
  - `failureKindOf` 恒返回 `transient` → 「跳过永久坏渠道」两条转红；
  - 内容指纹退回条数 → 「条数相同但内容在变」一条转红。
- **真机验收**：需重启 DSH。**与同批其他需重启改动一次验完**。

## 相关（本决策的后续）

⚠️ **本决策有一个直接后果**：门修严之后，**首次启动读不全会一直推不出东西** ——
这正是[启动不等读、用磁盘缓存](2026-10-06-startup-does-not-wait.md)要解决的问题。

两篇是**因果链**，不是并列关系：

|                                                     |                                                              |
| --------------------------------------------------- | ------------------------------------------------------------ |
| **本篇**                                            | 供给面没读全就**不推**（此前会推出半成品，显示 `CPA · xxx`） |
| [启动缓存那篇](2026-10-06-startup-does-not-wait.md) | 因为门变严 → 首次推不出 → 用**上次完整成功过的清单**兜住     |

⚠️ 但**那不是回归**：「什么都不推」不会给出**错归属**，而 `CPA · xxx`
是谎称那些模型属于 CPA —— 两者都坏，后者更容易让人按它得出错误结论。
