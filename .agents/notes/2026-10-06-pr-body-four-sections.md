# 决策：PR 正文四段、标签最多 3 个（2026-10-06）

状态：生效

## 问题

### 正文

原先的「六段正文」（目的 / 改了什么 / 为什么不用别的办法 / 怎么验 / 风险与代价 / 检查）
在**小改动**上是硬凑：

- 「回滚方式」这类段落是常识（`git revert` 谁都会），写它是噪音；
- 「为什么不用别的办法」在没有真实取舍时，只能把没考虑过的选项补写成「否决」；
- 「检查」把 CI 跑的东西再列一遍，而 CI 页面本来就是权威。

### 标签

标签体系检查时发现两件事：

- **子类型与主类型并列**（`bug` + `test`、`refactor` + `docs`）——
  它们在同一条筛选轴上，并列打让「按类型筛选」失效；
- **#20 打了 6 个标签** —— 「什么都沾一点」，筛出来的没有信息量。

读者要看的是**为什么、改了什么、前后差在哪**，不是 diff 的复述。

## 决策

**四段，可灵活变动**：

1. **为什么** —— 不写 diff 看不出的动机
2. **改了什么**
3. **前后** —— 行为对比
4. **怎么验**

相关**链接合并进末尾**，不散在各段里。

**术语改大白话**，删掉「回滚方式」这类常识段。

**大改动可以保留完整版**（确实有取舍时，「为什么不用别的办法」该留下），
**小改动别硬凑**。

## 判据

**如果一段只是把 diff 复述一遍，那段就不该存在。**

## 替代方案（强制）

- **固定四段、不许变**：会逼着有真实取舍的大改动把取舍删掉，或塞进
  「改了什么」里 —— 那正是「六段」在小改动上的毛病，反过来而已。**否决**
  （所以措辞是「可灵活变动」）。
- **只要三段（砍掉「前后」）**：「前后」是**用户能感知的差别**，
  而它常常不在 diff 里（比如「启动不再等读」这个差别，代码里看不到）。
  **否决**。
- **保留「回滚方式」**：本仓是 rebase merge + 单分支，回滚就是
  `git revert <sha>`。写它只增加维护面。**否决**。
- **不写 PR 正文，只靠提交信息**：提交信息是**逐提交**的（一个 PR 多个提交时，
  读者要自己合起来看），而 PR 正文回答的是**整批**的「为什么」。两者受众不同。
  **否决**。

## 标签（2026-10-06 同批收紧）

**最多 3 个 = 批次标签 + 主类型。**

**子类型（`test` / `docs` / `chore`）写进正文，不进标签。**
理由：它们与主类型在**同一条筛选轴**上，并列打会让「按类型筛选」失去意义 ——
想找「所有带测试的改动」，却因为有的打了 `test`、有的没打而得不出结果。

- **主意图明确时只打一个**。`bug` + `feat` 并列**允许**
  （「修一个 bug 顺带加一小块能力」确实常见），但要意识到它同时落在
  **两条筛选轴**里；主意图能一句话说清时就打那一个。
- **反例**：#20 打了 6 个（`bug,boundary-refactor,refactor,docs,test,chore`）——
  「什么都沾一点」，筛选结果没有信息量。

**判据**：**这个标签能不能用来筛选？** 不能（因为别人不一定打）就不该打。

**历史 PR 不批量改** —— 新 PR 按新规则走。
（例外：#35 补了 `test`，因为它与 #36 / #37 是同一类改动
——都修了别名/路由机制并补了判据，标签却只有 `bug`，**对照之下不一致**。）

## 影响

- 与[PR 纪律](2026-10-05-pr-discipline.md)并存：那份讲**技术纪律**
  （绝对 URL、ref 用 `main`、文本走文件、`gh label list`、rebase 改 sha 要回填），
  本文讲**正文结构**与**标签上限**。两者不冲突。
  ⚠️ 那份的「正文固定六段」已被本文取代，已在那边就地注明。
- 逐提交评论仍然保留（它服务的是「这个提交为什么这么切」，
  与正文的「整批为什么」不同层）。
