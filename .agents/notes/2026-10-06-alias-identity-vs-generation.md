# 决策：别名「识别」与「生成」分开判定（2026-10-06）

状态：生效

## 问题

面板里出现双重前缀的展示名：`WorkBuddy · wb/deepseek-v4.1-flash`
（同类还有 `wb/kimi-k2.6`、`wb/minimax-m3`），而契约是「渠道 · 裸名」。

根因是**两个不同的判断被写在同一个条件里**：

| 问题                            | 当时的依据   |
| ------------------------------- | ------------ |
| 这条 id 是不是别名（`resolve`） | 当前是否重名 |
| 要不要生成别名（`overlaps`）    | 当前是否重名 |

别名一旦写进 CPA 配置就是**持久**的，而重名关系随上游供给面变。
`wb/deepseek-v4.1-flash` 曾经重名（workbuddy + trae），别名落盘；
后来 trae 不再供给它 → `overlaps` 不再收录 → `resolve()` 失配 →
兜底分支把整个 `wb/xxx` 当裸名 → `name` 拼成 `WorkBuddy · wb/xxx`。

实测（2026-10-06）：72 条目录里 3 条命中，形态与本机 `config.yaml` 里
残留的别名段一一对应。

## 决策

**识别看拼形，生成看重名。**

- `resolve()`：凡 id 形如 `<已知渠道前缀>/<裸名>` 就认得出来 ——
  依据是**拼形**（`channelOfPrefix` 反查），与当前是否重名无关。
- `overlaps` / `aliasOf()`：仍然只看**当前重名** —— 不重名的模型配别名会
  让用户用原名调不到（[model-alias.ts](../../src/model-alias.ts) 头注的既有约束）。

实现上 `buildAliasTable(catalog, knownIds)` 多收一个 `knownIds`（目录里实际出现的 id），
把「已存在的别名」并入识别范围；`route-registry` 因此把别名表的构造**移到读目录之后**
（顺序错了就还是认不出）。

⚠️ **边界（已知并接受）**：「目录里有 `wb/x`」即视为合法别名 ——
即使配置里那条别名刚被清掉、CPA 还没重载。
**宁可多认一条别名，也不要双重前缀。**

## 替代方案

- **在 `routeOwnerOf` 里补一层「剥 `wb` 前缀」的猜测**：改动最小，但等于承认
  别名表可能认不出自己的别名，然后在多处打补丁；还要小心第三方自带的
  `vendor/xxx` 这类真含斜杠的 id（CPA 自带测试就有），猜错是静默错误归属。
- **让别名表以「配置里已写的那份」为准**：治本方向，但要读 CPA 配置并动
  `patchModelAlias` 的整段替换语义，风险大（`route-registry.ts` 明确警告过
  「少一个渠道就等于把已有别名删掉」）。目录本来就是配置的投影，
  用目录达到同样效果而不碰写入路径。
- **写别名时同步清理不再重名的旧别名**：治本的另一半，但「主动删配置」在
  整段替换语义下需要单独设计；而且目录已经是更可靠的真相源。
- **不管它，靠下次重推翻新**：`patchModelAlias` 整段替换确实会在下次重推时
  清掉多余别名，但**有窗口期**，且窗口期内的展示名就是错的。

## 影响

- 收益：展示名恒为「渠道 · 裸名」，不再依赖「当前是否重名」这个会漂的条件；
  同类问题（配置残留 vs 现算不一致）不会再从这条路出现。
- 代价：多认一条「配置里已不存在、但目录还在报」的别名，直到 CPA 重载 ——
  这是刻意选的偏保守方向。
- 判据：[tests/route-registry.test.ts](../../tests/route-registry.test.ts)
  的「别名在目录里、但该模型已不重名时，展示名仍要剥掉前缀」（改动前是红的）。
