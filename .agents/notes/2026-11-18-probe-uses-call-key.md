# 决策：模型健康探测用**调用密钥**，鉴权失败中断整轮（2026-11-18）

状态：生效

## 问题

2026-11-18 真机：面板「模型」弹窗点「探测一下」，**35 个模型全部「请求失败」**（0 正常 / 0 空回 / 35 失败）。

面板看起来像「这个渠道的模型全挂了」，实际是**一个前置条件不成立**：探测发的是
`POST /v1/chat/completions`，而它对 CPA 的默认通道（`CpaGateway.fetch`）拼的是
**管理密钥**（`Bearer <adminKey>`，那是 `/v0/management/*` 的钥匙）。CPA 在 `/v1/*`
上只认 `access.api-keys`（调用密钥 `CPA_API_KEY`），于是每一发都换来

```
HTTP 401  {"error":"Invalid API key"}
```

而 `probeOne` 把任何异常都收敛成「这一行 `failed`」—— 于是**一个鉴权错误被复制成
35 行「模型坏了」**，且逐行 detail 藏在 title 里，界面上只看得到「请求失败」。

实测（本机 CPA 8317，同一句 `hi`）：

| 钥匙                   | `/v1/models` | `/v1/chat/completions`      | `/v0/management/plugins` |
| ---------------------- | ------------ | --------------------------- | ------------------------ |
| 管理密钥               | 401          | 401 `Invalid API key`       | 200                      |
| 调用密钥 `CPA_API_KEY` | 200          | 200（`space-bunny` 正常答） | 401                      |

两张表说明「两把钥匙不同轴」这件事本身是对的、也是早就在文档里的（`docs/PLAN.md`）；
这次错在**探测这条新路径没跟着分轴**。

## 决策

1. **探测的发包必须带调用密钥**：`ops/index.ts` 的 `send` 用 `resolveApiKey()`
   覆盖 `authorization`（与 `readStableCatalog` 读 `/v1/models` 同款：`cpaFetch` 把
   `init.headers` 铺在管理密钥**之后**，于是覆盖有效）。
2. **没有调用密钥时不许退回管理密钥** —— 那必然 401。直接抛一条带 `status: 401`
   的错误，由探测域按下面的规则处理。
3. **401/403 中断整轮**：返回 `{ok:false, reason:'unauthorized'}`，并附一句
   「/v1 要调用密钥 CPA_API_KEY，管理密钥不被接受」。剩下几路不再发，
   **也不伪造逐行「失败」** —— 那一列正是误导的来源。
4. **逐次超时一路传下去**：`ProbeRequest.timeoutMs` 交给 `gateway.fetch` 的
   `timeoutMs`，且比本域的 `race` **宽 3 秒**。原先只在本域 race、HTTP 层的
   默认 20 秒先掐断，于是「允许慢模型」这句话从未生效。

判据：`tests/ops-model-health.test.ts`（授权头是调用密钥、401 中断且只跑一路、
没钥匙时零请求、`timeoutMs` 比 race 宽）。跑法与其余用例相同。

## 替代方案（强制）

- **在 `CpaGateway` 上加一个「调用密钥版 fetch」**：能把两把钥匙的边界收进一层，
  但它会把「哪条路径用哪把钥匙」变成网关的第二个职责，而网关现在的定位是
  「连接参数现取 + 前置 + 缓存」，与「按端点选钥匙」是两件事。**暂不引入** ——
  覆盖 `authorization` 的做法在 `readStableCatalog` 已有先例，两处同款更不容易漂。
  若以后出现**第三条**要打 `/v1` 的路径，再收口。
- **让探测走管理接口**（`/v0/management/...` 里有模型健康相关的口子）：上游没有
  「让这个模型说一句话」的管理端点，健康探测的本质就是一次真实推理请求。
- **逐行保留 `failed`，只在界面上加一句汇总**：35 行红字仍然会让人以为模型坏了；
  而且它继续白烧 34 次往返（每次探测都花真额度）。
- **拿字符串匹配 `Invalid API key` 判鉴权失败**：文案会变（上游有中文改写、
  也有 `Unauthorized` 形态）。判据用 HTTP 状态码，鸭子类型取 `status`，
  于是 `ops/` 不必引传输层的错误类。
- **给探测加长超时（比如 120 秒）**：治不了这个病 —— 401 是立刻返回的，
  与超时毫无关系；把超时调长只会让真正慢的模型多占着并发槽。

## 影响

- 修好之后「探测一下」才第一次给出**真实结论**：本机 workbuddy 35 行里
  一部分正常答、一部分是上游真不可用（`glm-4.7` 报
  `code 11102 模型未被该账号区域的上游注册`、`hunyuan-image-alpha-edit` 报
  `Backend [hunyuan-stream] is not supported`）—— 那些才是这条功能本来要暴露的信号。
- 代价：探测现在依赖 `CPA_API_KEY` 存在（正常安装路径上「一键准备」会写好它）。
  没写好的机器会得到**一条**可读错误，而不是 35 行假结论。
- 相关约束已回填：根 `AGENTS.md` 的活跃坑（两把钥匙）、`src/AGENTS.md` 的通道条、
  `docs/ARCHITECTURE.md` 的 F54。
