# 决策：模型路由只收托管渠道的可用凭据（2026-10-07）

状态：生效

## 问题

模型选择器里出现两类「有名字、用不了」的条目，2026-10-07 实机定位：

| 症状                                                            | 证据                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `Kimi · kimi-k2.8` / `MiMo · mimo-pro` 出现在选择器，但调用失败 | 该机的 kimi 凭据 `status=error` + `unavailable=true`，却仍报出 10 个模型 |
| `CPA · kimi-k2.7-code` / `CPA · kimi-k3`                        | 目录里有、归属算不出，被兜底成「CPA 自有」                               |

两条根因：

1. **供给面只问「这个凭据报了什么模型」，不问「它能不能用」。**
   `auth-files/models` 返回模型名，`auth-files` 同时返回 `disabled` / `status` /
   `unavailable` —— 我们只读了前者的返回值，后三个字段**一个都没读**。
   于是一个已报错、当前不可用的号报出的模型，与健康号报出的**完全同形**。

2. **认不出归属就兜底成 `CPA · xxx`。**
   那是在**谎称**：CPA 是代理层、不生产模型。把 Trae 的平台模型说成
   「CPA 自有」正是当初误判 Trae 那 11 条的同一个坑
   （见[模型归属决策](2026-10-06-model-ownership-and-image-capability.md)）。
   ���且它长得和「这轮读丢了归属」一模一样，下游无从分辨。

## 决策

**清单 = (CPA 目录里的 id) ∩ (托管渠道【可用】凭据供给面的并集)。**
标签只有一种来源：那个凭据属于哪个托管渠道。`CPA · xxx` 从代码里删除。

### 三道闸

| 闸                       | 位置                   | 判据                                                        |
| ------------------------ | ---------------------- | ----------------------------------------------------------- |
| 未托管渠道**连问都不问** | `readChannelModels`    | `channelOf(provider) === undefined`                         |
| 不可用凭据不供给模型     | `readChannelModels`    | `credentialUsable()`：`disabled` / `unavailable` / `status` |
| 认不出归属**不产出行**   | `buildCpaRouteProfile` | `plugin === undefined` 时 `continue`                        |

前两道是**过滤**（少收数据），第三道是**兜底删除**（不发明标签）。

### 两条不可省的性质

- **不靠特判渠道名**：判据是「有没有 spec」，所以 CPA 以后新增渠道自动被挡，
  不用改代码。前缀表（`ROUTE_PREFIXES`）同步收窄成只有托管渠道 ——
  这是第二道**结构性**保证：即便数据漏进来也挂不上标签。
- **认不出的健康度字段一律当「可用」**：上游加字段不该让已健康的渠道集体消失。
  「过滤过头」比多列几个调不通的模型严重（与 `failureKindOf`「宁可判成暂时」同取向）。

## 替代方案（强制）

- **只加健康度过滤，保留 `CPA ·` 兜底**：CPA 独占模型（远端目录里有、没凭据供的）
  仍会以「CPA 自有」出现在选择器，而它们**本来就调不通** —— 留着只是让人
  按错误的结论去用 → 否决。
- **给未托管渠道补 spec**：等于把职责范围扩到「CPA 有什么我们就管什么」，
  每个都要面板、账号操作、签到、能力表 —— 维护成本无界 → 否决（维护者定：
  本插件只管四个渠道）。
- **过滤放在建清单时而不是读供给面时**：读全部凭据再在下游丢弃，
  等于每次都替别人的渠道打 N 次管理接口，且「漏进来」的风险多一层 → 否决。
- **用 `/v1/models` 的 `owned_by` 判健康**：实测 `error` 的凭据照样带 `owned_by`
  标注，且该字段本就只是辅助标注、可为空（见模型归属决策）→ 否决。
- **让 `CPA ·` 变成可见的「未知归属」标记**：要改宿主侧选择器的展示契约，
  而宿主不认这个概念 → 否决。
- **按模型逐个发真实请求探测能不能用**：成本高、消耗额度、结果随时间变化 →
  否决（与 `channels/README` 里「为什么不能靠探测规避」同一条理由）。

## 影响

- **收益**：`CPA ·` 从代码里结构性消失；非托管渠道与不可用凭据的模型不再进清单；
  CPA 以后新增渠道不需要改本仓任何代码。
- **代价**：CPA 独占模型（无凭据供给）不再出现在选择器 —— 它们本就调不通；
  非托管渠道的账号从此不可用（面板本来就没有它们的页）。
- **判据**：`tests/route-registry.test.ts` 的「供给面只收托管渠道的可用凭据」
  四例 + `tests/channels-registry.test.ts` 的前缀表一例。
  **三道闸逐条变异验证过**：拆掉任一道，对应用例转红。
  ⚠️ 第一道闸拆掉时**清单断言仍会绿**（第二道闸兜着），
  所以判据里额外钉了「未托管渠道连问都不问」——
  否则那道闸等于没钉住，护栏是裸奔的。
- **未实测**：非托管渠道凭据的模型是否真的调不通（本决策假定调不通）。
